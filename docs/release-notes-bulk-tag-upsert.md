# 点位批量注册接口发布说明（待并入正式版本）

分支：`feat/bulk-tag-upsert`（基于 1.6.72 / 3a7a7dc）。已随 1.6.77 发布，版本要点见 [release-notes-1.6.77.md](release-notes-1.6.77.md)；本文件保留完整的接口契约、校验规则、基准和合流明细。

## 新接口：`POST /api/v1/project/bulk/tags`

一次请求把一批点写进指定通道、指定设备、指定嵌套标记组；通道或设备不存在时按请求创建。写库是一个事务，工程修订号只加 1。运行态只重建这一台设备，其它设备不停、不断连，北向组件不整体重启，也不进入热重载（`Reloading`）窗口。

主要调用方是 HSJM「PLC 程序上传后自动注册 IGW 拓扑」。`/Tag/AddTags`、`/api/v1/project/mutations` 和工程导入的行为不变。

### 请求

- 鉴权与 `/api/v1/project/*` 其它写接口相同。
- `If-Match` 可选。带上时按修订号做乐观并发，修订号不一致返回 409；不带时在配置提交锁内直接执行，适合串行写入的自动化调用方。`If-Match` 不是合法修订号时返回 400 `invalid_if_match`。
- 请求体上限 256MB（`ProjectBulkTagApi.MaximumRequestBytes`）。单个请求最多 200,000 项（`ProjectBulkTagValidator.MaxItems`）、`replaceGroups` 最多 10,000 条（`MaxReplaceGroups`），超出时整单返回 413 `too_many_items`，不做逐项校验、不写库。建议每个请求不超过 10 万项。一个请求只写一台设备；要写多台设备就发多个请求。

```json
{
  "channel": { "name": "泰兴PLC1", "driverId": "Siemens.S7", "settings": { "timeoutMs": "2000" } },
  "device": { "name": "S7Plus", "endpoint": "10.11.38.20:102", "settings": { "model": "S7-1500" } },
  "replaceGroups": [["DB490_OP100Alarm"]],
  "items": [
    {
      "groupPath": ["DB490_OP100Alarm", "Type", "Errors"],
      "name": "Error1",
      "address": "DB490_OP100Alarm.Type.Errors.Error1",
      "dataType": "bool",
      "access": "readWrite",
      "scanRateMs": 100,
      "description": null,
      "array": null,
      "metadata": { "source": "hsjm" },
      "stringLength": null,
      "engUnit": null
    }
  ]
}
```

- **通道**：按名称查找，不区分大小写。找不到就按 `driverId`/`settings` 创建。找到时 `driverId` 必须一致，否则返回 400 `channel_driver_mismatch`。已有通道的 `settings` 不覆盖。
- **设备**：在该通道下按名称查找，找不到就创建。找到时，`endpoint` 与请求不同则更新；`settings` 只补设备上缺少的键，已有键不覆盖（保留现场在界面上调好的参数）。
- **标记组**：`groupPath` 每段对应一级组，逐级查找或创建；空数组表示设备根层。
- **点**：按「所属组 + 点名」定位，不区分大小写。已存在就更新，不存在就新建。
- **replaceGroups**：每项是一个相对设备根的根组路径。同一事务里先删除这些组的整棵子树（包括其中的点），再写入 `items`。`items` 为空时，效果就是删除这些组。
- `dataType`/`access` 使用 IGW 原生枚举（camelCase 字符串）。数组点填写 `array`，格式与工程 JSON 相同。

### HSJM 调用方契约要点

- 数组点：`dataType` 必须等于 `array.elementType`；`array.lowerBounds` 可省略（默认全 0），给出时个数必须与 `dimensions` 相同；`dimensions` 每维大于 0。
- `access` 不要用 `"write"`：批量接口无法表达写确认方式，纯写点会被拒绝（`invalid_items`）；可写点请用 `"readWrite"`。
- `scanRateMs` 必须大于 0。
- 限额：每请求 ≤ 200,000 项、`replaceGroups` ≤ 10,000 条、请求体 ≤ 256MB（超出 413）；组路径 ≤ 16 层；名称 ≤ 128 字符且无控制字符；地址 ≤ 512 字符。
- 目标设备不能是模板实例。

### 名称规则

组名和点名不能为空，不能含 `.`，首尾不能有空白（与 IGW 界面规则一致；`canonical_path` 和运行态点位 id 都用 `.` 拼接），不能含控制字符（`char.IsControl`），长度不超过 128 个字符（`MaxNameLength`）。通道名和设备名规则相同；`replaceGroups` 的每段也要满足。

其它逐项限制（常量均在 `ProjectBulkTagValidator` 上）：

- `groupPath` 与 `replaceGroups` 每项最多 16 段（`MaxGroupDepth`）。更深的组嵌套会让运行态设备签名计算（JSON 深度上限 64）失败，写库后该设备无法应用、重启后整个网关无法启动，因此在入口拒绝。
- `address` 不能为空，长度不超过 512 个字符（`MaxAddressLength`）。
- `dataType`/`access` 必须是已定义的枚举值（数字形式的未定义值会被拒绝）；`scanRateMs` 必须大于 0。
- 同一请求内同一组下点名重复（不区分大小写）。
违反任一条时，整个请求返回 400 `invalid_items`，`details` 列出最多 50 条错误，每条包含 `index`（`-1` 表示通道、设备或 replaceGroups 本身的错误）和 `reason`。数据库不会有任何改动。

### 写库前的设备级工程校验

`/Tag/AddTags`、界面保存、工程导入都会对整个工程做 `ProjectStore.Validate`。为避免批量注册写入一个之后让这些入口全部失败的工程，宿主在写库前以内存工程为底构造“写入后的候选设备”（现有点 − `replaceGroups` + 请求点；更新已有点时按写库语义保留写确认等现场配置），对所有驱动做以下检查，任一不通过返回 400 且数据库不变：

- `ProjectStore.CheckDevice`（与全量校验共用同一套规则代码）：
  - 纯写点（`access: "write"`）必须配置确认方式。批量接口没有 `writeConfirmation` 字段，所以新建纯写点、或把没有确认方式的点改成纯写点会被拒绝；已有点本身带确认方式（确认点或仅协议确认）时保留并放行。
  - 确认点引用：目标必须存在于同一设备、可读、不指向自身、无循环。`replaceGroups` 删掉被保留点引用为确认点的点时会被拒绝。
  - 数组定义：`dataType` 与 `array.elementType` 一致、维度与下界数量一致、维度大于 0、元素总数不溢出、结构体布局等。
- 同级组名与点名不能完全相同（区分大小写，与 OPC UA NodeId 一致），否则节点 id 冲突。只检查本次请求新建的组和新增/改名的点；已有的重名不报。
- OpenProtocol 通道的设备设置（`resultProfile`/`sendProfiles`）。

以上返回 `invalid_items`，`detail` 给出前 5 条原因。只拦本次请求**新引入**的问题：目标设备上经其它入口遗留的违规（如无确认方式的纯写点、指向不存在点的确认点、类型与元素类型不一致的数组）会与“不做改动的现有设备”的检查结果比对后扣除，不会让与之无关的批量请求失败；但请求本身引入的违规（包括 `replaceGroups` 删掉被引用的确认点）仍会被拒绝。检查在候选设备的副本上进行，不修改运行中的工程。另外：

- 同名通道已存在但驱动不同，在预检阶段就返回 400 `channel_driver_mismatch`（写库时仍有同样的兜底检查）。
- 目标设备已存在且是模板实例（设置了 `templateRef`）时返回 400 `template_instance_not_supported`：模板实例的点来自模板展开，批量写入的点会与之冲突。写库层有同样的兜底检查。

预检与写库之间不持锁：若同时有其它保存改了同一设备，预检基于稍旧的工程（尽力而为）。

### S7 Classic 与 S7 Plus 地址混用校验

`Siemens.S7` 通道下，写入后设备内的全部点（包括这次没动的旧点，并已扣除 `replaceGroups` 删除的部分）必须全部是 Classic 绝对地址（如 `DB1.DBX0.0`、I/Q/M 区），或者全部是 S7 Plus 符号地址（如 `DB490.Type.Error1`）。两类地址混在一台设备里时，驱动在构造阶段就会报错，整台设备无法启动。因此这种请求在写库前就被拒绝，返回 400 `mixed_siemens_address_mode`，错误信息给出两类地址各一个例子，提示分到两台设备。无法解析的地址不参与判断，由驱动报错。非西门子通道不做这项检查。

### 响应

200：

```json
{
  "applied": true,
  "revision": "project-1043",
  "channelId": "…", "deviceId": "…",
  "created": 98211, "updated": 1789, "deleted": 5203,
  "deviceRestarted": true,
  "timing": "总计 6337ms：保存数据库 5617ms；应用运行态 720ms"
}
```

响应头 `ETag` 为最新修订号。`timing` 是分段耗时文本，内容以实际返回为准。

| 状态码 | `error` | 含义 |
|---|---|---|
| 400 | `invalid_request` | 请求体不是合法 JSON，或为空 |
| 400 | `invalid_if_match` | `If-Match` 不是合法修订号 |
| 400 | `invalid_items` | 违反名称/长度/层数规则、同组点名重复、地址为空、枚举值无效等（`details` 为逐项错误列表）；或写库前设备级校验不通过（`detail` 为原因） |
| 400 | `channel_driver_mismatch` | 同名通道已存在，但驱动不同 |
| 400 | `mixed_siemens_address_mode` | 同一设备内混用 S7 Classic 与 S7 Plus 地址 |
| 400 | `template_instance_not_supported` | 目标设备是模板实例 |
| 400 | `name_conflict` | 写库时触发同级重名唯一约束（UNIQUE / PRIMARY KEY），事务已整笔回滚 |
| 413 | `too_many_items` | `items` 超过 200,000 项或 `replaceGroups` 超过 10,000 条 |
| 503 | `persistence_failed` | 可重试的存储故障（SQLite 忙/锁定/IO/磁盘满/无法打开），事务已整笔回滚，数据库不变；可稍后重试 |
| 500 | `persistence_failed` | 不可重试的存储错误（如库内文档损坏、其它约束失败），事务已整笔回滚，数据库不变 |
| 503 | `database_unavailable` | 选择了外部主数据库，且主库断开或主库数据已被别处修改，暂停修改配置（与其它保存入口一致），数据库不变；恢复连接后可重试 |
| 409 | `revision_conflict` | `If-Match` 与当前修订号不一致，返回体带当前 `revision` |
| 500 | `runtime_apply_failed` | 数据库已提交，但按设备应用失败后回退的整体重读 + 整体应用也失败；网关进入降级状态，可显式重试运行态应用，已提交的数据不回退 |
| 500 | `bulk_failed` | 其它未预期异常 |

## 运行态应用范围

正常情况下只重建目标设备：

- 引擎只停、起这一台设备。已有点复用原来的数据中心句柄，删除的点注销，新点注册。其它设备的运行实例和连接不受影响。
- OPC UA 只替换这台设备的文件夹子树。订阅了已删除节点的监控项会收到节点不存在的状态，其它会话和订阅不受影响。
- 实时流默认不动。只有当删除的点正被某个实时流订阅时，才会让实时流整体重新同步一次。
- DCS 别名解析器在后台重建；读请求命中旧解析器直接返回，未命中时等待重建（最多 2 秒）再查一次；写请求一律按新工程解析（见下文“行为说明”）。

引用了这台设备的北向组件只重建组件本身，不再走全量应用（与界面局部保存同一套规则，见下文“与增量保存合流”）：

- 目标设备的新点或旧点中任一点配置了报警：重建报警引擎。
- 计算点、MES 上报任务（只看已启用且开放流程的任务）、计划任务中，任一处引用了本次被删除、新增或条目被重建的点，或引用了这些点的上级组/设备本身（例如 MES 任务的 `GroupRef` 等于 `通道.设备.组`）：重建对应组件。中文名称同样能识别。单次涉及的点超过 2,000 个时，改按“是否引用这台设备”判断。

以下情况仍改走全量应用。全量应用期间网关处于热重载窗口，DCS/REST 数据读写会短暂返回 503：

- 目标设备是模板实例（批量注册本身已拒绝模板实例，这里只是兜底）。
- 按设备应用本身失败（例如 OPC UA 同步抛错）：同一次请求内自动回退为整体重读 + 整体应用，成功即返回成功（耗时里记一段“局部应用失败，改为整体应用”）；只有整体应用也失败才进入降级。
- 配置协调器已处于降级状态（之前有已提交但未应用到运行态的变更）。这时会整库重新读取并全量应用，把先前的变更一起补上，全量应用成功后才解除降级。
- 数据库已提交，但读回该设备失败。这时进入降级状态，重试时走全量重载。

## 行为说明

- 更新已有点时，只更新请求里能表达的字段：地址、类型、访问方式、扫描周期、数组定义、组归属。现场配置的缩放、死区、报警、写确认等选项保留不变。
- 请求里为 `null` 或省略的可选字段（`description`、`engUnit`、`stringLength`、`metadata`），在更新已有点时保留库内原值，不会被清空。
- 点名大小写以请求为准：已有点 `a` 被请求里的 `A` 命中时，库内名称会改成 `A`，`canonical_path` 同步更新，库内点 id 不变。
- DCS 别名：批量注册完成后，旧解析器能命中的别名读取立即返回，不等待重建。**注意**：因此在后台重建落地之前（大工程下约为秒级），读取一个被改挂到另一台设备的逻辑设备别名，仍可能解析到旧的物理点；写入不受影响（总是按当前工程解析）。同步兜底构建按工程单飞，并发写者共享一次构建。新设备的别名在旧解析器上未命中时，读取会等待进行中的后台重建（最多 2 秒，仍未完成则同步构建）后再查一次，不会误报“点位不存在”。写入（含 `CheckValidity`）一律用按当前工程构建的解析器，逻辑设备改挂到另一台 PLC 后不会写到旧 PLC；解析器构建失败时写入返回 503。
- 请求取消：写库提交之前取消（如客户端断开），事务回滚，按取消处理（不再报 `persistence_failed`）。一旦提交成功，读回设备与运行态应用不再响应取消，必须做完，避免数据库领先运行态、网关进入降级。
- 显式重试运行态应用（`GatewayHost.RetryRuntimeApplyAsync`）只在降级状态下执行；未降级时直接返回成功，不做全量应用。
- 实时流只在删除的点正被订阅时整体重新同步；其它情况下 `RealtimeRevision` 保持不变，已订阅的点继续收到新值。

## 存储层改动

- 批量注册新建的组和点，id 改用按时间有序的 GUID（`Guid.CreateVersion7`，仍是 32 位十六进制）。已有行的 id 不变。
  - 原因：随机 GUID 会让每一行插入都落到百万行主键 B 树的随机位置，页缓存装不下。
  - 效果：有序 id 让一批插入集中写在索引尾部，百万点工程上追加的耗时与空工程接近。
- 批量写事务改用私有页缓存连接（`ProjectDatabase.OpenAsync(ct, privateCache: true)`），其它连接仍用共享缓存。
  - 共享缓存模式是表级锁，长写事务期间，同进程读 `tags` 表的请求要等到写事务结束。改用私有缓存后，读者按 WAL 快照并发读取。
  - 写者之间仍由 `BEGIN IMMEDIATE` 加忙等待串行。实测批量写入期间发起的界面修改会等到批量提交，然后按修订号返回冲突或正常执行，不会报数据库锁错误。
  - **前提**：批量写事务要在 Microsoft.Data.Sqlite 的命令超时（默认约 30 秒）内完成。实测 30 万点的批量写入耗时 16.5 秒，期间的界面修改等了 14.9 秒后正常返回。如果单个批量事务超过约 30 秒，同时等待的其它写操作会以“数据库被锁定”失败。这也是建议每个请求不超过 10 万项的原因之一。
- 设备重启时复用刚算好的设备签名（10 万点设备约省 0.3 秒）。

## 基准数据

测试环境：i7-8700K（6 核 12 线程）、32GB 内存，工程库在 NVMe（Samsung 980 PRO，系统盘临时目录），Release 构建，服务器 GC。

测试期间本机另有开发会话在运行，每次测量前都记录了负载：其它进程持续占用约 2～4 个逻辑核，主要是 node 约 1.3～1.9 核、git find 约 0.4 核（后期已结束）、另一个 IGW.Runtime 0.1～0.4 核，偶尔还有其它 dotnet 编译进程。因此绝对耗时偏悲观，同一场景重复运行波动约 ±20%，以同一轮内的相对比较为准。

每个场景都先发一次丢弃的预热请求（进程内首次调用含 JIT 和首次分配），表中给出预热后的数值，冷启动数值单独列出。

各层计时口径：

- **仓储层**：`IProjectRepository.BulkUpsertTagsAsync`，即单事务写库。
- **协调器层**：`ProjectConfigurationCoordinator.ExecuteBulkAsync`，包括写库、读回设备、投影进健康工程；运行态应用为空操作。
- **宿主层**：按接口端点的顺序计时，依次为客户端序列化请求、服务端 `JsonSerializer.DeserializeAsync(ProjectStore.Options)` 反序列化、`ProjectBulkTagValidator.Validate` 校验、`GatewayHost.ApplyBulkTagsAsync`。
  - `ApplyBulkTagsAsync` 包括写库、读回设备，以及在引擎中重建设备（Simulator 驱动）、替换 OPC UA 子树（OPC UA 服务端开启，随机端口）、实时流判定。
  - “服务端耗时”指反序列化、校验、`ApplyBulkTagsAsync` 三项之和。请求体放在内存流中，不含 HTTP 传输和 Kestrel 开销。
- **预置场景的比值**：在同一进程内，预置前后各测一次空工程基线（同一时段、同样负载），比值 = 预置库中位数 ÷ 两次空工程基线合并后的中位数。

```powershell

dotnet run --project benchmarks/IGW.ProjectStorage.Performance -c Release -- --scenario bulk-preseeded --rounds 3
dotnet run --project benchmarks/IGW.ProjectStorage.Performance -c Release -- --scenario bulk-10x
dotnet run --project benchmarks/IGW.ProjectStorage.Performance -c Release -- --scenario bulk-host --opcua true
```

### 仍存在的瓶颈与建议

1. **写库本身**（仓储层 2.8～3.5 秒）仍占宿主层耗时的 70%～80%，受整机负载影响也最大。
   - 其中 `ix_tags_address` 等二级索引依然有随机插入。
   - 把逐行执行改成同步调用的实验看不出收益，未采用。
   - 进一步优化需要改表结构或索引策略（例如批量写期间延后建索引），本次未做。
2. **读回设备 `LoadDeviceAsync`**：0.5～1.1 秒。可以改为直接用请求内容和写库时已知的 id 组装设备定义，省掉这次读回；但要保证与数据库读取的结果逐字段一致，改动较大，建议另行评估。
3. **读快照会被批量写事务阻塞**：`OpenReadSnapshotAsync` 开启事务时用的是默认的 `BEGIN IMMEDIATE`，这会拿写锁，所以要等批量写事务结束。
   - 在 WAL 模式下改为延迟事务（`BEGIN DEFERRED`），首次读取即可建立一致快照，不再与写者排队。
   - 这会影响导出路径，建议单独改。
4. **每次请求结尾，标签分页有 0.3～0.8 秒的短暂阻塞**，出现在批量提交之后。
   - 推测原因：连接不走连接池，批量写连接关闭时可能是库上最后一个连接，SQLite 在关闭时执行检查点并删除 WAL 文件，与新打开的读连接短暂互斥。
   - 可以保留一个常驻的只读连接，或调整 WAL 检查点策略。但与“导入时关闭连接后原子替换数据库”的设计有关，建议另行评估。

## 与增量保存合流

`master` 在同一时期引入了界面“增量保存”（大工程页面只提交变化节点的 `Batch` 修改，内存合并工程后按设备应用运行态）。两边各有一套“按设备应用运行态”的实现，合并时统一为一套，两个入口共用：

| 关注点 | 统一后的唯一实现 |
|---|---|
| 协调器 | 只有一个局部应用回调 `applyPatch(ProjectPatch)`。界面保存由 `ProjectMutationPatcher` 生成补丁；批量注册把读回的设备投影成同形的补丁（`ChangedDevices` = 该设备）。 |
| 采集引擎 | `RuntimeEngine.ApplyDevicesAsync(变化设备, 删除设备)`：签名不变跳过；删除的点先注销再起新循环；旧循环排空超时改用全新条目；删除/改名的旧设备停掉并注销；停设备与算签名并行。 |
| 数据中心 | `DataHub.UpdateDefinition` 与批量注册的 `ReplaceDef` 语义一致：原子发布新定义，值类型/数组形状变化时置“等待初值”；注销或同名重注册时摘掉点订阅并释放设备需求。 |
| OPC UA | `SyncDevices(变化设备, 删除设备, 删除通道, 重建条目)`：保留 master 的并行建节点与启动时一次加锁填值；每台设备按批量注册的子树对齐（同名节点原地更新、删除节点释放钉点/推送、新节点带当前值、重建条目在新句柄上重新注册推送）。 |
| 宿主 | `GatewayHost.ApplyPatchedRuntimeAsync`：不置热重载标志；实时流只在点表参数变化或被删除的点正被订阅时重建；北向组件按上面的规则只重建受影响的组件；未完成的组件重建、OPC UA 改绑、实时流补建都记为待办，由重试、下一次局部应用或全量应用补做。实时流版本号的写入统一经过 `SetRealtimeRevision`。 |

合流时顺带修复了界面增量保存路径上的问题（批量注册路径此前已修复）：

- **排空超时共用条目**：旧设备循环未在宽限时间内退出时，界面保存仍复用它持有的数据中心条目，新旧两个循环同时写同一条目。现在改用全新条目，并改绑 OPC UA 推送、必要时重建实时流。
- **删除被监控的点不释放**：界面删除一个正被 OPC UA 客户端监控的点后，钉点和推送注册不释放，设备会一直被轮询；槽位被新点复用后推送也可能冻结。现在删除节点时按监控项数释放，客户端之后删除死监控项也不会重复释放。
- **提交后取消导致运行态分叉**：请求在写库提交后被取消时，局部应用中途放弃（master 的回退条件是“未取消”，取消时连整体重读都不做），运行态落后于数据库却不进入降级。现在提交后不再响应取消，局部应用和回退的整体应用都会做完。
- **局部应用失败的回退**：保留 master 的体验——按设备应用失败时，在同一次调用内（提交后不响应取消）整体重读数据库并整体应用，成功即对调用方报告成功；只有整体应用也失败才进入降级（待办为整体应用，显式重试或下一次保存时补上）。批量注册同样适用。局部应用中途失败时，已停止未重启的北向组件和未同步的 OPC UA 地址空间记为待办，由这次整体应用一并重建，保证运行态与数据库一致。
- **类型变化后仍以 Good 提供旧值**：界面把点改了数据类型，复用条目时旧值仍按旧类型以 Good 质量提供给 OPC UA/REST，现在置为“等待初值”直到新类型首次采集。
- **批量注册清空设备的 KEP 属性**：master 起设备写库会整列写回 `kep_properties_json`，而批量注册读回的设备文档没有带这一列，补设置/改 endpoint 时会把 KEP 属性清空。现在设备文档带上 KEP 属性；批量新建的组和点使用列默认值 `{}`。

行为变化：

- 只改说明（描述）的界面保存不再重启设备的采集循环（设备运行签名不含说明），说明就地刷新到缓存定义和 OPC UA 节点。
- 界面保存的实时流不再因“有设备变化”就整体重建，与批量注册一致，只在被删除的点正被订阅或点表参数变化时重建。
- 批量注册读回的设备在投影进工程前做一次内存压缩（`ProjectMemoryCompactor.CompactDevice`，字符串只在该设备内共用）。

合流后复测（同一台机器，另一开发会话在跑，整机 CPU 占用由约 30% 逐步升到 50%～90%）：

- `bulk-host --opcua true`：3 次运行的 10 万点服务端中位数分别为 4.70 / 5.56 / 6.62 秒，与负载同步上升；增量主要在写库（中位数 3.6 → 5.0 秒），运行态部分稳定：重启设备约 0.46～0.55 秒，同步 OPC UA 约 0.30～0.34 秒，预检 40～80 毫秒。负载最低的一次与合流前（4.56 秒）持平。DCS 并发读 3,414～4,087 次，0 失败。
- 同一场景新增界面单点保存（约 100 万点工程，改 1 个点的扫描周期，所在 10 万点设备重启）：0.47～1.15 秒（负载较低的那次），高负载时 0.94～2.64 秒；其中“保存数据库”段约 20 毫秒（首个编辑约 0.26 秒，含内存合并用的位置索引首建：批量注册投影出的新工程实例没有缓存索引）。

## 与 DCS `/Tag/AddTags` 共存

问题（HSJM 端到端测试发现）：批量注册建的工程通道（如 `泰兴线_PLC1`）里的设备也带 `dcsLogicalDevice`（`S7_{ip}`、`S1500_{ip}`、`S7Plus_{ip}`，供 `通用.{逻辑设备}.…` 别名读取）。`/Tag/AddTags` 原先选“第一个同驱动、且含带 `dcsLogicalDevice` 设备的通道”，于是批量注册之后，其它系统的 AddTags 会把设备落进这个工程通道，而不是 `通用`；对批量已注册的同一台 PLC 调 AddTags，还会按 `dcsLogicalDevice` 匹配到并改写批量管理的设备。

修复：

- **归属标记**：批量注册写库时，给新建或更新的设备 settings 写入 `dcsManagedBy = "bulk"`（常量 `ProjectBulkTagMetadata`）。只改这一个键，其它 settings 仍按“只补缺失键、不覆盖”处理。已有设备（包括 AddTags 建的设备）被批量注册写入一次后，即由批量注册管理。写库前的候选设备预检同样带上这个键，与写库结果一致。
- **AddTags 选通道**：只考虑含“AddTags 管理的 DCS 设备”（有 `dcsLogicalDevice` 且不是 `dcsManagedBy=bulk`）的通道；找不到时沿用原来的 `通用` / `通用_{CommType}` 规则。OPC UA 按服务器地址选通道时，跳过含批量管理设备的通道。
- **AddTags 找设备**：在选中的通道里按 `dcsLogicalDevice` 匹配时，忽略批量管理的设备。
- **拒绝接管**：AddTags 某一项的逻辑设备（`{CommunicationType}_{ip}`）在工程任意位置已由批量注册管理时，整批拒绝（与其它逐项校验相同，工程不变），错误信息形如 `索引 N:逻辑设备 S1500_x 由批量注册管理（通道.设备），请使用 /api/v1/project/bulk/tags`。不这样做会另建一个同名逻辑设备，使 `通用.S1500_x.…` 别名变成歧义（两处都读不到）。
- **别名解析不变**：`通用.{逻辑设备}.…` 别名对两类设备都照常解析（解析器只看 `dcsLogicalDevice`，不看归属标记）。
- **兼容性**：没有批量注册设备的工程，AddTags 行为完全不变。本修复之前已由批量注册建好的设备没有归属标记，要等下一次批量注册写到它时才会被标记；在那之前 AddTags 仍可能按旧规则选中它所在的通道。HSJM 每次上传都会重新注册，升级后重跑一次即可全部补上标记。

## 已知问题 / 后续

1. ~~**大设备上的小改动耗时偏长**~~（已改善，提交 448343e）：HSJM 端到端测试中，在 32.4 万点的设备上改 3.7k 个点共耗时约 10.8 秒；其中写库约 7.3 秒，重启设备约 3.1 秒。改动如下：

2. **数组单个元素的别名读取**：按 DCS 别名读取数组点的单个元素（如 `…EXEC_BITS[3]`）返回“点位不存在”。别名解析器只把 `通用.{逻辑设备}.` 前缀换成物理前缀后，按完整点位 id 查找；数组元素不是独立点位 id，因此当前实现不支持元素级别名，需要按数组点整体读取后自行取下标。是否应当支持元素别名（以及物理路径的元素读取是否支持）尚待确认，确认前请调用方按整个数组读取。

## 与外部主数据库复制合流（1.6.77）

master 在 1.6.76 引入了外部主数据库（SQL Server/PostgreSQL/MySQL）：本机 SQLite 仍是工作库，每张业务表挂触发器，把增删改记入待同步队列 `_igw_outbox`，后台引擎推到主库；主库断开时暂停修改配置。合流时的处理：

- **复制不遗漏**：触发器是库结构的一部分，与写入所用的连接无关。批量写入虽然走私有页缓存连接、长事务、预编译 INSERT/UPDATE 和临时表 `bulk_ids`，`tags`、`tag_options`、`tag_groups`、`channels`、`devices`、`project_meta` 的每一行以及 `replaceGroups` 的删除都会进入队列；临时表不在 main 库中，不复制。新增测试 `BulkTagReplicationCaptureTests` 按引擎启动时的方式挂触发器后执行批量写入，逐行核对队列。
- **暂停修改配置**：`ApplyBulkTagsAsync` 与界面保存一样检查 `IDatabaseSync.ConfigurationWriteBlockedReason`，非空时不写库，返回 503 `database_unavailable`（可重试）。
- **立即同步**：写库成功后调用 `IDatabaseSync.Nudge()`，运行态应用失败也照样触发（数据已在本机 SQLite 中）。
- **大批量走整表复制**：同一张表待同步的不同主键超过 20,000 个时，引擎改为整表复制。10 万点的批量注册会让 `tags`、`tag_options` 整表复制到主库；百万点工程上需要数十秒，在后台进行，不阻塞请求。另外触发器会给每一行写入多一次队列插入，本文前面的基准是在未启用外部主库（无触发器）时测得的。
- 合流后后端全量测试 2,005 项：2,000 通过、4 项跳过（需真实数据库服务端）、1 项为已知的 `MesWritebackCycleTests` 时间敏感用例（两次全量运行各失败不同参数组合，单独运行通过）。

### 外部主数据库下的批量注册提速

上面“大批量走整表复制”和“触发器多一次队列插入”两点已改掉：

- **写库不再逐行触发**：检测到本机库有待同步队列时，批量写入在自己的事务里临时去掉 `tag_groups`、`tags`、`tag_options` 上的复制触发器，把写过的点和组的主键记进临时表，提交前恢复触发器，再用一条集合语句写进队列（`ReplicationOutbox`）。
  - 队列内容与触发器写出的逐字相同，同步引擎不用区分来源。
  - SQLite 的建删触发器随事务提交和回滚，`BEGIN IMMEDIATE` 期间也没有其它写者，所以不会漏记。
  - 通道、设备、`replaceGroups` 的删除、修订号仍由触发器逐行记录。
  - 只是暂停触发器不够：被暂停的触发器每行仍要判断一次条件，10 万点还要多花约 7 秒。
- **主库端按主键批量替换**：只有待同步主键超过 20,000 且超过表行数一半时，才整表复制；其余按主键删除后批量写入。
  - 每轮取 20,000 条。
  - 500 行以上的写入：SQL Server 用 SqlBulkCopy，PostgreSQL 用二进制 COPY。
  - SQL Server 的大批量删除先把主键导入临时表，再用一条 `DELETE … JOIN` 完成。
- **实测数据**：本机的 SQL Server Express、PostgreSQL 17、MySQL 9.7，场景是预置 50 万点后批量注册 10 万点、再改 1,000 点。测试是 `DatabaseReplicationTests.Bulk_registration_replicates_by_key_without_resending_the_table`，运行时设置 `IGW_DB_TESTS=1 IGW_DB_BULK_SEED=500000 IGW_DB_BULK_ITEMS=100000`。

| 主库 | 写库（改前 → 改后） | 同步到主库（改前 → 改后） |
|---|---|---|
| SQL Server | 14.0 → 4.8 秒 | 36.3 → 9.9 秒 |
| PostgreSQL | 14.8 → 4.8 秒 | 20.3 → 6.7 秒 |
| MySQL | 14.2 → 4.4 秒 | 118.8 → 27.0 秒 |

- **空工程单请求 10 万点，仓储层**：基准加 `IGW_BENCH_CAPTURE=1` 挂上触发器，从约 12 秒降到约 3 秒；不挂触发器时约 2.5 秒。
- **MySQL**：服务端默认关闭 `LOAD DATA LOCAL`，仍用多行 INSERT，是三种主库里最慢的。
