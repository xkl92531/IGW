# IGW 全协议大规模 PLC 读写引擎设计

## 1. 背景

IGW 需要服务大型产线：工程可能包含约 50 个同时工作的工位、数十台 PLC、几十万到 100 万个已配置点位。常规任务可能要求约 200 ms 周期，少量关键任务可能包含数百个点并要求 10 ms 级目标周期；运行期间也可能出现数万到十万点的集中写入。

现有运行时已经具备每设备独立循环、截止时间调度、内存 DataHub、变化总线、按需采集和部分故障隔离，但协议执行层仍存在固定批量与逐点访问瓶颈：

- OPC UA 和 S7 的计划仍存在固定 1000 点拆批；
- 通用 PLC 计划固定为 256 点，部分驱动实际批量更小；
- 标量写队列每轮最多执行 10 项；
- EtherNet/IP、三菱 MC 等路径仍包含大量逐点读写；
- 驱动没有统一表达连接后协商得到的动态读写能力；
- 写入成功目前没有统一的强制回读验证合同。

本设计补齐现有百万点架构中的“协议原生读写执行层”。它不替换现有 DataHub、MES 画布或工程结构。

## 2. 已确认目标

1. 用户只配置业务需要的采集周期和业务写入关系，不配置高速/普通通道、线程数、批量大小或连接数量。
2. 所有协议根据字段权限、服务器能力、协议限制和实际响应自动生成读写计划。
3. 多台设备并行工作；单台设备、单个 DB、单个地址块或单个点位失败不能阻塞其他范围。
4. 周期采集使用协议原生批量读取；支持变化推送的协议可对实时条件和监控使用订阅。
5. 所有写入必须被验证。普通字段采用目标点回读一致；命令类写入采用通用确认点条件。
6. 初次写入后，未验证成功的字段最多重写 10 次；每次只重写仍失败的字段。
7. 数据/权限/类型/容量错误不关闭设备会话；只有确认的网络、传输或协议会话失效才重连。
8. 支持几十万点读写需求，但不虚假承诺任意 PLC、任意点位布局都能达到 10 ms 或 200 ms；必须显示实际容量和超期原因。
9. 数组依据来源格式、协议元数据、真实地址和同构结构识别，不依据 `Bolts`、`CellData` 等业务名称猜测。
10. 原生数组、扁平数组、结构体数组、多维数组、嵌套数组、非零下界、稀疏及不规则数组都使用统一逻辑数组描述；画布和监控不展开成成千上万个配置项。

## 3. 非目标与物理边界

- Windows/.NET 不是硬实时系统；周期为调度目标，必须记录实际平均、P95、P99和超期。
- IGW 不能突破 PLC 的 PDU、报文长度、通信负载、扫描周期、最大会话数或服务器 OperationLimits。
- 跨 PLC 的多个写入无法由通用协议保证物理原子性。IGW 提供阶段屏障、逐点结果和失败隔离，不承诺分布式事务回滚。
- 不允许通过隐藏坏质量、丢弃写请求、无限缓存或把容量错误伪装成离线来获得表面吞吐。
- “十万点同时写入”表示 IGW 可以有界接收、自动分组并完整返回结果，不代表一个 PLC 能在一个网络往返内物理完成十万点写入。

## 4. 总体架构

新增四个清晰边界：

1. `DriverCapabilitySnapshot`：驱动连接后提供当前会话的动态能力。
2. `ProtocolPlanCompiler`：把点位需求编译成协议原生读写批次。
3. `DeviceIoScheduler`：按截止时间、优先级、时间预算和在途限制执行批次。
4. `WriteVerificationEngine`：执行写入、回读/确认、比较和最多 10 次选择性重写。

数据流：

```text
工程/MES/QC/北向需求
        ↓
需求合并（点位最短周期）
        ↓
协议能力 + 字段权限
        ↓
不可变协议计划
        ↓
每设备 DeviceIoScheduler
        ↓
批量读取 / 订阅更新 / 批量写入 / 批量验证
        ↓
DataHub 批量更新与逐点结果
```

同一设备默认保持单会话有序执行。只有驱动明确声明可安全并发时，才允许有限在途请求。不同设备继续并行。

## 5. 动态协议能力

### 5.1 设备会话能力

驱动连接成功后生成能力快照，至少包含：

- 最大读取点数、字节数、地址跨度；
- 最大写入点数、字节数；
- 最大安全在途请求数；
- 是否支持连续块读写；
- 是否支持离散多变量读写；
- 是否支持订阅或事件推送；
- 是否支持注册节点/预编译符号；
- 数组和结构体的整体/切片能力；
- 建议写后验证等待时间；
- 能力版本。

能力改变时只重编译受影响设备的计划，不重启整个工程。

### 5.2 字段操作能力

每个字段编译为通用操作能力：

- `CanRead`
- `CanWrite`
- `CanSubscribe`
- `CanVerify`
- `PermissionSource`
- `LastOperationStatus`

权限来源按优先级合并：

1. 当前登录会话的实际权限；
2. OPC UA `UserAccessLevel`、`AccessLevel`、`AccessLevelEx`；
3. 协议区域规则，例如 Modbus 输入寄存器只读；
4. 工程定义的访问权限；
5. 最近一次实际操作返回码。

浏览得到的权限只是初值，实际服务返回码始终具有最终权威。权限变化后更新字段能力并增量重编译。

## 6. 自适应批量控制

固定 `MaxTagsPerRead=1000` 不再作为所有设备的执行上限。

每个设备分别维护读、写和验证读的自适应窗口：

1. 优先使用服务器或协议协商出的明确上限；
2. 未声明上限时，从驱动提供的安全初始值开始；
3. 连续成功后缓慢增大窗口；
4. 遇到“操作过多、请求/响应过大、PDU 超限”等容量错误时二分降批；
5. 降批只重试当前批次，不关闭连接；
6. 记住当前会话已验证的安全窗口；
7. 重新连接或服务器指纹变化后重新协商；
8. 同时受点数和编码后字节数两项约束，不能只看点数。

容量错误、权限错误、地址错误和类型错误必须与传输错误分开分类。

### 6.1 未声明上限不是无限容量

服务器返回 `0`、空值或无法读取 `MaxNodesPerRead/MaxNodesPerWrite` 时，只能说明服务器没有声明协议计数上限，不能推导出单次请求可安全承载 10,000 点。驱动必须使用保守探测窗口（OPC UA 初始建议 256～512 点，其他协议由帧/PDU能力确定），并按实际响应逐步增长。该窗口只是单次服务调用规模，不限制工程总点数。

自适应控制同时观察：

- 服务返回的容量状态码；
- 单次请求耗时及近期 P95；
- 请求/响应编码字节数；
- 超时、取消和服务器资源不足；
- 写入快速通道的排队延迟。

多节点请求出现 `BadRequestTimeout` 或等价的服务级超时时，先把它视为当前批次超过实时处理能力：二分降批并在同一健康会话内重试当前范围。只有单节点请求仍超时且连接/会话探测同时失败时，才升级为会话或传输故障。

客户端主动取消、手动硬重连或运行时停机导致的 `BadRequestInterrupted` 属于预期中断，不得显示为 PLC 故障，也不得污染容量学习结果。

## 7. 读取设计

### 7.1 周期采集

MES 周期任务和明确要求周期快照的消费者使用批量 Read。每个周期按设备拆分，读取完成后批量更新 DataHub。MES 不直接调用驱动，也不遍历工程树。

当执行时间超过周期时不补跑历史轮次，只保留最新一次到期需求，并报告周期超期。

### 7.2 实时变化

支持服务器推送的协议可对实时条件、QC、监控和其他变化消费者使用 Subscription/事件推送。字段只读不妨碍订阅；是否可订阅由服务器服务能力和创建监控项的实际结果决定。

订阅不能替代需要明确本轮新鲜度的周期读取。发生以下情况时执行批量补读：

- 订阅刚建立或恢复；
- 数据时间超过消费者要求；
- 订阅序列出现缺口；
- 服务器不支持订阅；
- 创建监控项失败或达到服务器容量上限。

### 7.3 各协议计划

- **OPC UA**：读取 `MaxNodesPerRead` 等 OperationLimits；周期任务批量 Read；实时消费者使用多订阅并自动分组；支持时注册重复读取节点。
- **S7 Classic**：按 DB 和连续字节范围合并，依据协商 PDU 拆包，本地按偏移解码。
- **S7 Plus**：按符号批量读取；数组和结构体优先整体读取。
- **Modbus**：按线圈/离散输入/输入寄存器/保持寄存器分区，遵守协议帧上限并连续块读。
- **Omron FINS**：按内存区域和连续地址块读取。
- **Omron EtherNet/IP / CIP**：使用 Multiple Service Packet、数组读取和受控并发，替代大量逐点任务。
- **三菱 MC**：连续设备块读取后本地切片，替代逐点请求。
- **MQTT**：直接由消息推送更新 DataHub，不使用模拟轮询。
- **模拟器**：直接批量内存访问，用于性能和故障注入测试。

## 8. 统一数组结构识别与执行

### 8.1 当前问题

现有 MES 范围树在前端和后端分别判断纯数字子组、`Name[index]` 与 `Name_index`。该实现只能覆盖部分展开形式，并且仍然受展示名称影响：同一真实数组换一种导出格式就可能不再折叠，普通数字业务组也可能被误判；前后端算法变化不同步时，预览、保存和运行结果还会不一致。

数组识别必须移到后端唯一的 `ArrayShapeRecognizer`。工程导入、OPC UA 浏览、MES 范围目录、QC 和运行引擎都消费同一个识别结果，前端不再自行用名称正则重建数组。

### 8.2 识别证据和优先级

识别器使用有来源的证据链，而不是数组名称：

1. **显式类型元数据**：现有 `ArrayDef`、OPC UA `ValueRank/ArrayDimensions`、Siemens DB/UDT 的 `ARRAY[..] OF`、KEP 数据类型及厂商配置字段；
2. **协议地址语法**：OPC UA NodeId/符号地址中的索引段、S7 字节或符号布局、寄存器连续地址及协议原生数组长度；
3. **来源格式树结构**：KEP JSON、OPC UA Browse、Siemens DB、IGW JSON 各自由独立解析器输出规范化路径段和索引段；
4. **严格结构回退**：只有元素结构完全同构、下标关系可证明、物理地址或 NodeId 也支持该关系时，才折叠未知厂商的扁平树。

展示名称只用于最终标签，不作为数组证据。仅仅因为节点叫 `0`、`1`，或名称以 `_0` 结尾，不足以判定数组。证据不足或结构冲突时保留原始节点并显示“数组结构未确认”诊断，不静默猜测。

每个识别结果保留：来源格式、识别器版本、证据、置信等级、原始路径和物理绑定。重新导入或移动展示目录时可以稳定重建，不依赖当前 UI 层级。

### 8.3 统一逻辑模型

在兼容现有 `ArrayDef` 的基础上增加递归逻辑描述：

- `ShapeKind`：`Rectangular`、`Sparse`、`Jagged`；
- `Dimensions` 与 `LowerBounds`：矩形多维数组，支持非零和负下界；
- `ElementSchema`：标量、结构体或另一个数组，可表达结构体成员数组、数组套数组和嵌套结构体数组；
- `BindingKind`：`NativeNode`、`AddressPattern`、`ExpandedElements`；
- `AddressPattern`：用规范化索引占位符解析物理地址，不为每个元素复制配置；
- `IndexMap`：只保存稀疏、不规则或厂商无法模板化的例外映射；
- `SourceShape`：保留来源的原始数组声明和路径格式。

规则数组不得展开为 N 个永久 `TagDef`。一个十万元素数组在工程、MES 参数选择器和 QC 树中仍是一个逻辑项；具体元素、切片和结构体成员按需虚拟化、分页加载。只有协议本身暴露为离散叶子时，执行计划才在内存中生成临时物理叶绑定。

矩形的嵌套数组可规范化为多维形状；真正的交错数组保留递归 `Jagged` 结构，不能伪装成矩形。稀疏数组保留实际下标集合，不能用不存在的元素填零。

### 8.4 必须兼容的结构类别

识别和往返必须覆盖：

- 标量数组及字符串数组；
- 一维、二维和任意合法秩的矩形数组；
- 数组结构体、结构体内数组、数组内结构体再含数组；
- 数组套数组和交错数组；
- 下界为 0、1、负数或其他值的数组；
- 连续、稀疏和存在缺口的下标集合；
- OPC UA 单一原生数组节点，以及服务器展开为元素/成员节点的形式；
- Siemens 优化/非优化 DB 中的原生数组及嵌套 UDT；
- KEP JSON 中按配置树展开、按地址索引展开和原生数组类型三种形式；
- `A[0]`、`A[0,1]`、`A[0][1]`、数字路径段、下划线等厂商外观，但这些外观必须由对应格式解析器和地址证据解释，不能由通用名称正则直接决定；
- IGW JSON 导入导出的显式逻辑数组，完整保留结构、下界、绑定和 JSON 映射名称。

后续出现新厂商形式时增加一个 `IArrayFormatRecognizer`，不得继续在 MES 页面或目录构建器中追加零散正则。识别器输出统一候选和诊断，因此扩展一种格式不需要修改上报、QC 和运行逻辑。

### 8.5 冲突、演进和兼容

- 同一下标元素的成员名、类型、数组形状或访问权限不一致时，不合并为普通同构数组；能表达为不规则结构时使用 `Jagged/Sparse`，否则给出冲突位置。
- 同名节点按完整来源路径和物理地址区分；移动展示目录不改变物理绑定身份。
- 旧版逐元素工程加载时执行只读迁移预览；只有证据完整时自动升级为逻辑数组，并保留旧元素标识的可逆映射。
- 工程导出后再导入必须得到相同逻辑结构和协议，不允许退化成几千个标量组。
- MES 模板保存逻辑来源和成员路径；套用到新 DB 时按结构映射，不缓存旧工程的物理 TagId。

### 8.6 读写与画布行为

逻辑数组进入 `ProtocolPlanCompiler` 后按物理绑定执行：

- 原生数组节点优先整体或切片 Read/Write；
- 连续地址数组按协议上限分块；
- 展开叶数组按可批量的 NodeId/符号集合读写；
- 稀疏和交错数组只访问实际存在的元素；
- 部分失败保留逐元素质量，不把整个数组和连接统一置为 Bad；
- 写后验证只回读本次写入切片，失败时只重写不一致的元素或连续范围。

MES 画布默认显示一个数组范围，可选择起始、数量、维度切片或结构体成员；“填入本组全部点”只增加逻辑范围引用，不生成上万个字段配置。搜索、展开和右侧预览必须分页/虚拟滚动，切换节点不丢失已经选择的范围。

## 9. 通用写入计划

核心不识别 `MESFlag`、`PLCFlag`、`Complete` 等项目字段名称。所有写入统一编译成通用阶段计划：

```text
阶段 1：同阶段设备并行、设备内协议批量写
   ↓ 达到阶段成功条件
阶段 2
   ↓
阶段 N
```

普通批量写只有一个阶段。有握手或顺序要求的项目由画布节点顺序或 API 中的阶段显式表达。每阶段包含：

- 任意点位集合；
- 必要/非必要字段；
- 阶段成功条件；
- 通用验证合同；
- 超时和调用来源；
- 写入代次。

同阶段跨设备并行。阶段中的必要字段全部验证成功后才允许进入下一阶段。跨设备失败不执行物理回滚，但必须返回完整逐点结果。

## 10. 强制写后验证

### 10.1 基本流程

所有写入执行：

```text
初次 Batch Write
       ↓
等待驱动建议的验证间隔
       ↓
主动 Batch Read 或确认条件读取
       ↓
类型归一化比较
  ├─ 一致：该字段完成
  └─ 不一致：只重写该字段，最多 10 次
```

最多执行一次初写和十次重写。成功字段立即从后续重试集合移除。第十次重写后仍未验证成功，返回 `WriteNotVerified`，包含期望值、实际值、质量、尝试次数和总耗时。

验证读必须发往真实设备，不能使用尚未确认新鲜度的 DataHub 或订阅缓存。

### 10.2 两种通用验证合同

1. **目标回读一致**：普通参数、结果、数组和结构体字段写入后，读取同一目标并比较。
2. **确认点条件**：命令、脉冲或会被 PLC 程序立即复位的字段，等待项目指定的任意确认点满足条件。

不能把命令位简单按“目标值仍相等”验证，否则 PLC 已消费并复位时会被误判，并可能重复触发十次。确认点由通用 TagId 和比较条件表达，不依赖任何字段名称。

因为系统要求所有写入都必须验证：字段既不可回读、也没有配置确认点时，写入应在发送前被拒绝为“无法验证”，不能假装成功。

### 10.3 类型比较

- Bool、整数、枚举：按目标 PLC 类型精确比较；
- Float/Double：先归一化到目标位宽，再比较编码后值，避免主机类型转换误差；
- String/WString：按 PLC 编码、声明容量和截断结果比较；
- 数组/结构体：按元素和成员比较，记录失败索引/路径，只重写失败的连续范围；
- 回读 Bad/Uncertain：不算验证成功；
- 协议返回 Good 但回读不同：分类为写入未确认或 PLC 程序覆盖，不分类为连接故障。

### 10.4 写入代次

每个字段维护单调递增的写入代次。如果验证期间到达更新值：

- 旧代次立即停止重写；
- 旧调用返回 `Superseded`；
- 新值成为唯一允许继续写入和验证的意图。

这防止旧重试覆盖更晚的控制命令。

## 11. 读写调度与背压

每台设备只有一个长期调度器，不为每点创建线程、Timer 或永久 Task。内部维护：

- 周期读取截止队列；
- 高优先级交互/控制写；
- 普通写与可合并最新值；
- 写后验证队列；
- 订阅维护和补读任务。

取消固定“每轮最多写 10 项”，改为协议批量上限和时间预算。调度器使用加权截止时间策略：

- 已到期的关键写与验证获得低延迟；
- 周期读取不能被连续写入永久饿死；
- 大批读写按可取消边界让出执行权；
- 队列必须有界；达到上限时返回明确过载状态，不能无限占用内存；
- 可合并写只合并同一点的旧代次，顺序敏感写不得静默合并。

### 11.1 写入快速通道

大量周期读取不得把交互写、业务回写或写后验证堵在一个长时间在途 Read 后面：

1. 读取计划切成有界时间片，每个物理批次结束后先检查写入和验证队列；
2. 新写请求唤醒设备调度器，并在下一个安全边界优先执行；
3. OPC UA 等明确支持并发服务且服务器会话容量允许时，可自动启用独立控制会话，将 Read/Subscription 与 Write/Verify 隔离；该行为由驱动学习并管理，不暴露给用户配置；
4. S7 Classic、Modbus 等必须保持单连接有序的协议，通过更小读取时间片和协议原生批量写实现让行；
5. 控制会话创建失败时自动退回单会话优先级调度，不影响采集会话；
6. 写入快速通道只改善 IGW 排队延迟，不伪造 PLC 的真实网络和执行耗时。

设备必须分别记录“写请求进入队列”“首次发送”“PLC响应”“回读验证完成”时间，从而区分 IGW 排队、网络、PLC服务和验证四段延迟。

## 12. 故障隔离

统一错误范围：

- **点位级**：权限、类型、只读、值范围、单点不存在；
- **块级**：DB 不存在、地址跨度错误、部分数组失败；
- **容量级**：请求过大、操作过多、服务器资源不足；
- **会话级**：Session/SecureChannel 失效；
- **传输级**：Socket、网络、远端关闭；
- **过载级**：周期无法满足、内部队列达到上限。

点位、块和容量级错误不得关闭连接。会话或传输级错误才重置协议对象。单个 DB 失败只对该块退避并复探，其他 DB 继续执行。

所有驱动通过统一操作结果表达 `Scope`（点位/块/容量/会话/传输/过载）、`RetryDisposition`（不重试/缩小批次/同会话重试/重建会话）和原始协议状态码。运行引擎不得再以“驱动抛出了异常”为依据无条件断开会话。

读取批次超时的默认行为是：当前块标记为暂时 Bad、缩小批次、保留连接、保留写队列并安排短延迟复探。只有明确的 SecureChannel、Session、Socket、远端关闭或连续单点探测失败才进入通道级硬重连。写入权限、类型、值范围、单点地址和写后验证失败同样不得关闭连接。

## 13. 可观测性

监控中心按设备显示：

- 当前读、写和验证批量；
- 协商上限与当前自适应安全值；
- 每秒样本数、写入数和网络字节数；
- 请求平均、P95、P99耗时；
- 目标周期、实际周期和超期次数；
- 读队列、写队列、验证队列深度；
- 在途请求数；
- 降批、重写和验证失败次数；
- 部分失败的 DB、地址块、数组范围或点位；
- 数组识别来源、置信等级、逻辑元素数、实际绑定数和结构冲突；
- “周期无法满足”“写入未确认”“容量受限”等独立状态。

容量问题和数据错误不能显示成 PLC 离线。

## 14. 兼容性

- 现有工程文件和点位结构保持兼容；
- 小工程不要求修改配置；
- MES 画布现有读、上报和响应回写节点语义保持；
- 原有单次写 API 继续存在，内部自动包装成单阶段强制验证写；
- 批量 API 扩展为可选多阶段计划和逐点验证结果；
- 不根据字段名称推断业务语义；
- 不根据业务名称推断数组；数组结构由统一识别结果驱动；
- 不向用户暴露批量大小、线程数和高速模式。

## 15. 验收与证据边界

### 15.1 合成验收

- 50 台模拟设备、总计 1,000,000 点；
- 全量目标周期 200 ms；
- 多个约 500 点、10 ms目标周期的快速任务；
- 100,000 点集中写入并强制验证；
- 注入单点、单块、单 DB、单设备和网络失败；
- 连续运行至少 30 分钟；
- 无无限队列、无补跑风暴、无静默丢写、无数据错误导致整设备断线；
- 输出 CPU、工作集、分配率、GC、吞吐、P95/P99、队列峰值和失败分类。
- 用 10,000 和 100,000 元素逻辑数组验证工程加载、MES 选择和 QC 页面不做全量 DOM 展开。
- 对原生、扁平、多维、结构体、嵌套、交错、非零下界和稀疏数组执行识别、切片读写、部分质量及写后验证测试。
- KEP JSON、OPC UA Browse、Siemens DB 和 IGW JSON 均执行导入、导出、再导入的结构等价测试。
- 以 2,477 个 OPC UA 点复现现场扫描：服务端对大批 Read 注入 10 秒超时后，客户端必须自动降批并恢复采集，会话保持在线；同期排队写入必须执行且得到逐点结果。
- 手动硬重连取消在途 Read 时允许出现内部 `BadRequestInterrupted`，但设备状态不得产生虚假的网络故障，重连完成后扫描和写入队列正常恢复。
- 单点只读、类型错误、地址不存在和写后验证不一致均不得导致其他点、DB或整个设备离线。

### 15.2 协议认证

OPC UA、S7 Classic、S7 Plus、Modbus、Omron FINS、Omron EtherNet/IP、三菱 MC、MQTT 分别记录：

- 设备/服务器型号和固件；
- 点位类型、连续程度、数组/结构体布局；
- 协商能力和最终自适应批量；
- 每轮请求数、字节数和耗时；
- 实际平均/P95/P99周期；
- 读写及验证吞吐；
- PLC 通信负载、主机 CPU、内存和网络吞吐。

合成测试证明 IGW 内核能力；只有真实硬件认证才能证明某型号 PLC 在某点位布局下达到指定周期。二者必须分别报告。

## 16. 实施边界

实现顺序按依赖组织，但最终统一验收后交付：

1. 统一数组逻辑模型、格式识别器注册表和迁移诊断；
2. 动态能力与字段权限接口；
3. 协议计划编译器和自适应批量控制；
4. DeviceIoScheduler 读写与验证队列；
5. 强制写后验证和写入代次；
6. OPC UA 订阅/批量读写及原生/展开数组绑定；
7. S7、Modbus、Omron、EtherNet/IP、三菱和 MQTT 原生计划；
8. 前端统一消费数组目录并实现虚拟化选择；
9. 监控指标与通用批量 API；
10. 全量回归、数组格式矩阵、合成压力和真实协议认证。

任何实现阶段不得通过降低逐点结果正确性、跳过写后验证或扩大断线范围换取吞吐。
