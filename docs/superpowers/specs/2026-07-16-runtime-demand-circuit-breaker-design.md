# Runtime 按需连接与通信熔断设计

## 目标

Runtime 在没有任何数据消费者时不主动连接 PLC；PLC 不可达或驱动出现“连接成功但读取立即失败”时，不得形成高速重连循环。正常在线设备的采集周期、写入和热重载行为保持不变。

## 已确认规则

- 数据需求包括：启用的 MES 采集流程、OPC UA 监控项、Quick Client/REST 近期读取、计划任务、告警/计算点订阅，以及启用的历史或 MQTT 全量消费者。
- 没有任何数据需求时，设备保持未连接；出现需求后自动连接。
- Quick Client/REST 的一次读取沿用现有活动窗口，默认在最后一次访问后保持 30 秒需求，随后无其他消费者即可断开。
- 任一通信阶段连续失败 3 次后，设备进入 30 秒熔断。
- 熔断期间不连接、不读取，待写请求立即返回设备不可用。
- 30 秒后只允许一次半开探测。首次有效读取成功则关闭熔断并恢复正常采集；连接或读取再次失败则立即重新熔断 30 秒。
- 日志只记录进入熔断、半开探测、恢复连接等状态变化，避免同类错误高速刷屏。

## 设计

### 数据需求模型

`DataHub` 继续作为点位需求的统一来源：

- `Touch` 表示有期限的临时需求，供 REST、Quick Client、计划任务使用。
- `Pin/Unpin` 表示持续需求，供 OPC UA 和 MES 使用。
- 点订阅在注册点位期间形成持续需求，覆盖告警和计算输入点。
- 全量订阅存在时，所有设备均有数据需求，覆盖历史记录和 MQTT 全量发布。

`DeviceLoop` 在连接前检查本设备是否存在点位需求、临时设备级操作或待写请求。没有需求时保持断开并以低频可唤醒等待，不执行连接和读取。浏览设备地址空间等不依赖已配置点位的操作使用临时设备级需求，操作结束后释放。

设备扫描模式仍保留原语义：`all` 模式在设备存在任一需求后扫描该设备全部点；`active` 模式只扫描活动点。按需连接只决定是否建立连接，不替代原扫描模式。

### 熔断状态机

设备通信状态增加 `Closed / Open / HalfOpen`：

1. `Closed`：正常连接和采集；连接或读取失败累计计数。
2. 连续第 3 次失败：断开驱动、标记点位坏质量、进入 `Open` 30 秒。
3. `Open`：只等待取消、配置重载、写/数据需求信号或熔断到期；到期且仍有需求时进入 `HalfOpen`。
4. `HalfOpen`：只执行一次连接和有效读取；成功回到 `Closed` 并清零计数，失败立即回到 `Open`。
5. 无需求时主动断开并等待；重新出现需求后，如果熔断未到期仍遵守原熔断期限。

现有可选的 KEP 风格冗余/降级设置继续保留。主备切换优先于内置熔断；主备路径都无法形成有效读取时才进入熔断。

## 测试与验收

- 无点位需求启动设备循环，驱动连接次数保持为 0。
- `Touch`、持续点订阅或全量订阅出现后，设备自动连接并开始读取。
- 所有需求释放且活动窗口到期后，设备自动断开且不再读取。
- 模拟驱动每次读取立即失败：前 3 次后停止重试，熔断窗口内连接/读取次数不再增长。
- 半开探测失败会再次熔断；半开读取成功会恢复正常周期。
- 真实安装服务复测：PLC 全部不可达时，日志不再连续刷屏，CPU 从持续多核占用降至空闲水平。
- 运行完整 .NET 测试、前端测试、类型检查和生产构建。

## 非目标

- 不修改设备扫描周期配置。
- 不改变 MES 采集流程的业务状态机。
- 不自动删除或禁用工程中的设备、点位和采集任务。
- 不用简单全局延时掩盖驱动错误。
