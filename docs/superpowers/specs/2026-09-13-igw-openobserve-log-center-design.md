# IGW OpenObserve 统一日志中心设计

状态：用户于 2026-09-13 确认采用 OpenObserve 方案，并批准本设计方向。

## 目标

为 IGW 独立设计并实现统一日志中心。新版本以本机 OpenObserve 作为运行日志、状态日志和性能日志的唯一查询与聚合引擎，不再用 `igw-*.log` 文本文件承担日志中心的数据存储与查询。

本次改造同时覆盖日志产生、异步传输、故障缓存、OpenObserve 进程管理、查询接口、保留策略、存储目录迁移、Vue 页面和安装包。PLC 采集不能等待日志系统，也不能因为 OpenObserve 不可用而停止。

## 已确认选择

- OpenObserve 随 IGW 安装并在本机自动启动，现场不需要另外部署日志服务器。
- Runtime 通过 OpenTelemetry SDK 和 OTLP/HTTP 向 OpenObserve 写入结构化遥测。
- 不增加本地 SQLite 或另一套结构化日志库。
- OpenObserve 不可用时允许使用有容量上限的磁盘传输队列；该队列只负责待发送批次，不作为日志查询库。
- 新日志中心使用 IGW 自己的信息架构、组件、文案、视觉样式和交互，不复制其他项目的前端设计或代码。
- 原有 `igw-*.log` 文件保留在原目录，不删除、不自动导入 OpenObserve；升级后的新业务日志只进入 OpenObserve。
- `/api/v1/runtime-logs` 兼容接口保留一个版本，但数据来自 OpenObserve，不再读取旧文本文件。

## 总体架构

新增 `IGW.Observability` 项目，封装结构化字段、OpenTelemetry Provider、OTLP 导出、失败缓存、查询构造、保留策略、正文存储以及日志目录迁移。`IGW.Core`、`IGW.Runtime` 和各北向模块只依赖明确的遥测接口，不直接拼接 OpenObserve SQL 或管理 OpenObserve 进程。

新增 `IGW.LogService` 可执行项目。Windows 中注册为独立的 `IGW Log Service`，Linux 中注册为独立 systemd 服务。该服务读取 `%ProgramData%\IGW\observability.json` 或 Linux 对应数据目录中的配置，启动并守护随包提供的 OpenObserve 子进程，并执行存储目录迁移。日志服务可以独立重启；Runtime 不依赖它成功启动。

Runtime 创建 `RuntimeTelemetry`，把 `ILogger`、`ActivitySource` 和 `Meter` 接入本机 OpenObserve。日志传输失败时，OTLP 请求批次写入所选日志根目录下的 `export-cache`，恢复后按至少一次语义重放。缓存默认上限为 128 MiB 或 512 批，达到上限时丢弃新批次并累计可见计数。

Web UI 只访问 IGW Runtime 提供的受保护接口。OpenObserve 的地址和凭据不发给浏览器，也不直接嵌入 OpenObserve 原生页面。

```text
PLC / OPC UA / MES / REST / Runtime
                |
       结构化日志、指标、调用链
                |
       OpenTelemetry OTLP/HTTP
                |
       有界 export-cache（故障时）
                |
    本机 OpenObserve（IGW Log Service）
                |
       IGW 受保护查询与设置接口
                |
         IGW Web 日志中心
```

## 日志分类与字段

统一日志流命名为 `igw_logs`，所有可筛选字段使用稳定的 `igw_` 前缀。至少提供以下五类视图：

| 分类 | 主要来源 | 必须记录的结构化字段 |
| --- | --- | --- |
| 总览 | 下列所有分类 | 时间、级别、分类、消息、状态、关联 ID |
| PLC 采集 | `IGW.Core/Engine.cs` 的实际批次读写 | 通道、设备、数据块或区域、批次、点数、有效数、异常数、结果、错误 |
| 接口调用 | ASP.NET Core、HttpClient、MES、SignalR、WebSocket | 方向、方法、路径或目标、协议、状态、耗时、重试、任务和节点 |
| PLC 状态 | 设备连接、断开、重连、恢复及读取质量变化 | 设备、旧状态、新状态、原因、事件类型、发生时间 |
| 采集性能 | 现有批次与协议计时 | 配置周期、实际间隔、排队、驱动、协议、本地处理、总耗时、超期、吞吐 |

所有批次参与性能统计，但正常采集按设备和批次汇总，不为每个点位生成一条日志。失败、恢复、慢批次和错过周期单独记录。详细诊断按设备限时开启，避免大 DB 产生不可控日志量。

同一次采集、流程判断、MES 上报和响应回写共用 `trace_id`，每一步使用独立 `span_id`。任务和节点写入 `igw_task_id`、`igw_node_id`，供日志详情跳转到当前 IGW 流程画布。

凭据、Authorization、Cookie、令牌、密码、连接串密钥和 URL 查询参数必须脱敏。接口正文默认只写受限长度的脱敏摘要。需要查看完整正文时，实现 IGW 自有的关联正文存储：正文作为受保留策略控制的内容存放在所选 observability 根目录，通过随机 payload ID 按需读取，不建立另一套结构化查询库。

## IGW 前端设计原则与界面

前端只继承 IGW 当前产品已经使用的 Element Plus、字体、蓝色品牌色、严重度颜色、间距尺度、双语机制和权限行为。不得复制其他项目的 Vue 模板、CSS、组件树、文案、图表源码、图标组合或页面布局；功能需求由本规格重新实现。

`/logs` 采用“范围导航 + 时间走廊 + 详情抽屉”的 IGW 自有布局：

- 页面顶部为 IGW 标准标题区，提供刷新和日志设置；其下使用一条紧凑状态带展示 OpenObserve、缓存、丢弃和迁移状态。
- 左侧“范围导航”按总览、PLC 采集、接口调用、PLC 状态、采集性能组织分类，并显示当前查询范围内的数量徽标；窄屏时折叠为下拉选择。
- 中部“时间走廊”按时间倒序呈现记录，以严重度色条、时间、对象、摘要和耗时形成统一行结构；支持后端分页和 20、50、100、200 条页大小。
- 右侧详情使用抽屉，不遮挡当前查询条件；显示中文字段说明、原始结构化属性、关联链、正文入口和流程节点入口。
- 筛选器放在可展开的 IGW 标准筛选栏中，支持最近 15 分钟、1 小时、24 小时、7 天或自定义时间，以及通道、设备、DB、流程、级别、关键词和关联 ID。已启用条件以可单独清除的筛选标签显示。
- 总览顶部使用四个紧凑指标块展示匹配记录、异常或离线次数、当前分类核心指标、查询或运行耗时。
- 趋势区作为时间走廊上方可折叠分析区，展示记录数、错误数、平均耗时和 P95；图表从零独立实现，并支持鼠标和键盘读取时间桶。
- PLC 状态以设备状态条和离线事件时间轴呈现。超过 60 秒没有新观测时显示“状态未知”，不能把历史在线记录当成当前在线。
- 总览的最近异常、慢采集和接口失败使用同一时间走廊的保存视图，不另造三种卡片模板。
- 保留策略和存储目录沿用 IGW 现有设置弹窗风格，支持永久保留或 3 至 3650 天，并显示迁移进度和失败回滚原因。

页面查询可取消过期请求。静默刷新只用于第一页的相对时间范围；自定义历史时间、翻页、详情打开和用户尚未提交的筛选不会被自动刷新覆盖。请求失败时保留上一次成功结果并提供重试。

`/performance` 跳转到 `/logs?category=performance`。现有 `/monitor` 仍保留 MES 流程与实时运行能力，日志详情可带任务和节点参数跳转过去。QC、工程树实时值和写入功能不受此次日志中心改造影响。

## 后端接口

新增以下接口，并继续由 IGW 现有管理权限保护：

- `GET /api/v1/log-center/status`：日志服务、缓存、正文和迁移状态。
- `POST /api/v1/log-center/query`：固定模板查询、聚合、设备状态和分页结果。
- `PUT /api/v1/log-center/retention`：更新 OpenObserve 自有日志、指标、调用链及正文的保留时间。
- `PUT /api/v1/log-center/storage`：验证目标目录并启动后台迁移。
- `GET /api/v1/log-center/payload/{id}`：列出关联正文。
- `GET /api/v1/log-center/payload/{id}/{part}`：分段读取或下载正文。
- `GET /api/v1/runtime-logs`：把旧参数转换为新的日志查询，并返回旧 DTO 形状。
- `PUT /api/v1/runtime-logs/settings`：兼容调用新的保留和目录设置。

查询只允许后端定义的分类、字段、排序和聚合模板。时间范围最大 31 天，单页最大 200 条，页码和搜索长度有上限；字符串值统一转义，前端不能提交任意 SQL。OpenObserve 请求超时不超过 12 秒，返回内容限制为 8 MiB。

## OpenObserve 配置与安全

首装时生成随机用户名、强密码、实例 ID 和可用端口。密码经 IGW 本机密钥保护后写入 `observability.json`，密钥文件限制为服务账户可访问。升级沿用现有配置，不重新生成凭据。

OpenObserve 仅监听 `127.0.0.1`，关闭遥测上报，显式设置数据、数据库、WAL、流和索引目录，确保数据全部落入用户选择的日志根目录。首版固定打包 OpenObserve `1.0.0` 开源版本，并由 IGW 独立验证依赖清单、许可证和 SHA256；客户安装期间不下载 `latest`。

遥测导出和日志查询使用后端凭据。自动 HTTP 埋点排除 OpenObserve 健康检查、查询和 OTLP 导出地址，防止日志递归。

## 安装、升级和目录迁移

Windows 安装器增加“日志保存位置”步骤，默认 `%ProgramData%\IGW\observability`，支持中文和空格路径，安装前验证可写性及磁盘空间。安装包包含 `IGW.LogService` 和固定版本 OpenObserve，先初始化 observability 配置，再注册并启动 `IGW Log Service`，最后启动 `IGW Gateway`。

Linux 构建包提供相同的初始化参数和独立 systemd 单元，默认 `/var/lib/igw/observability`。Windows 与 Linux 的 Runtime 都可以在日志服务未就绪时启动并采集。

从界面切换日志目录时，后台按以下顺序执行：

1. 标记迁移并暂停 OTLP 直发，后续批次进入有界缓存。
2. 日志服务停止 OpenObserve。
3. 复制数据、数据库、WAL、流、索引、正文和缓存，并持续写入迁移进度。
4. 使用新目录启动 OpenObserve 并执行健康检查。
5. 健康检查通过后保存新配置、恢复导出并补发缓存。
6. 任一步失败则恢复旧目录，保留失败原因，不删除源目录。

升级继续使用原目录。卸载程序移除两个服务和程序文件，保留工程、授权、OpenObserve 数据、旧 `igw-*.log` 和 observability 配置。

## 旧日志切换

升级后停止 `FileLoggerProvider` 作为业务日志 Provider 和查询源。旧日志目录保持不变，用户仍可直接打开历史文本文件。为排查 OpenObserve 自身无法启动的问题，日志服务只保留有大小上限的启动诊断输出；该输出不承载 PLC、MES 或接口业务日志。

旧工程中的 `LogRetentionDays` 和 `LogStorageDirectory` 在首次启动时迁移为 observability 配置。成功迁移后保留字段读取兼容，但新设置由 observability 配置负责，避免工程热重载改变日志存储位置。

## 故障与性能边界

- 日志写入、批量导出、缓存和清理都在采集线程之外执行。
- OpenObserve 停止时采集继续，页面明确显示不可用、积压和丢弃数量。
- 缓存采用至少一次重放，允许极少量重复；不承诺服务长期故障时无限无损。
- 磁盘满、目录不可写或缓存达到上限时优先保障采集，并产生可观测的丢弃计数。
- 目录迁移失败时自动回滚旧目录；源目录和已复制目录都不自动删除。
- 日志中心查询不能抢占 PLC 协议操作，也不能额外读取 PLC。
- 性能对比至少记录启用前后的扫描吞吐、CPU 和内存，确保正常日志级别没有显著降低采集能力。

## 实施顺序

1. 新增 Observability 配置、凭据保护、OpenObserve 依赖固定和独立日志服务。
2. 新增遥测导出、失败缓存、查询接口、保留策略、正文存储和目录迁移。
3. 在采集、状态、性能、MES 和接口边界补齐结构化字段与关联链。
4. 独立实现 IGW 统一日志中心，增加旧链接和旧接口兼容。
5. 更新 Windows/Linux 安装与升级逻辑，构建包含 OpenObserve 的安装包。
6. 完成模拟、真实本机 OpenObserve、故障恢复、性能和安装包验收。

## 验收标准

1. 使用隔离 Simulator 产生成功采集、失败、离线、恢复、慢批次、MES 业务失败和接口超时，能在真实本机 OpenObserve 中查到，并能按关联 ID 串联。
2. 日志查询的分类、组合筛选、分页、聚合、趋势、详情、正文和流程跳转均有前后端测试。
3. 停止 OpenObserve 后 IGW 继续采集，待补发数量增加；恢复后缓存重放且丢弃数保持可解释。
4. 大工程验证日志中心不增加 PLC 读取，比较扫描吞吐、CPU、内存并记录结果。
5. 中文和空格目录下验证 OpenObserve 元数据、WAL、索引、日志、正文和缓存的实际写入位置。
6. 验证运行中目录迁移成功、失败回滚、升级沿用目录和卸载保留数据。
7. Windows 网站模式、现有配置界面、QC、MES 流程和权限分别通过回归；Linux 验证 systemd 启停和自定义日志目录。
8. 后端、前端、安装脚本和固定依赖校验全部通过；生成的新安装包记录版本、大小和 SHA256。

## 不在本次范围

- 不连接外部或云端 OpenObserve 集群。
- 不引入 OpenTelemetry Collector。
- 不把每个 PLC 点位的每次值变化写成日志。
- 不自动解析和导入旧 `igw-*.log`。
- 不承诺超过有界缓存容量后的日志零丢失。

## 原创性与隔离边界

- IGW 前端需求、线框、组件、文案、CSS、图表和交互均在本仓库独立设计与实现。
- 不复制或改名使用其他产品的前端源文件，也不以像素级复刻作为验收目标。
- 后端按 OpenTelemetry 与 OpenObserve 的公开协议独立实现，代码命名、配置格式、错误模型和服务边界使用 IGW 自有约定。
- OpenObserve 可执行文件按其开源许可证独立固定版本、校验和并随安装包提供，许可证文件必须进入安装包和依赖清单。
- 完成前执行源码相似性人工复核，重点检查 Vue 模板、样式、文案、组件结构和静态资源，确认没有误带其他项目的前端实现。
