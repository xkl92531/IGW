# IGW 耗时操作反馈检查（2026-09-11）

用户要求：点位数量较大时必须说明正在读取/处理，避免操作后像卡住；同时检查其他入口。此记录区分界面反馈与真实执行完成，不能用动画代替服务端成功结果。

## 统一行为

- 用户发起的网络等待和本地批量处理显示具体阶段；执行期间避免重复提交。
- 耗时本地操作先让出一次界面刷新；大批点位、结构体识别分批处理，并在提交结果前核对原任务/节点是否仍有效。
- 成功、失败、取消都结束各自的加载状态。旧请求不得提前结束新请求的提示或覆盖新选择。
- 普通 HTTP 配置请求提供顶端非阻塞等待提示，250ms 内完成的请求不闪烁；较长请求显示实际等待秒数，不显示虚构百分比。
- 健康、实时订阅、日志后台刷新、验证作业轮询不使用全局阻塞动画；手动操作使用已有或新增的局部反馈。

## 范围与证据

检查覆盖 Web 页面的请求、文件读取和主要批量操作；普通单字段输入、单行选择、折叠等即时操作不加入固定延时或假加载。WPF 另补了采集字段填充、结构体识别的状态、禁用与分批刷新。Web 自动测试、类型检查及 Docker 中的延迟请求视觉验证记录位于 `artifacts/protocol-qa/loading-*`。

原生浏览器下载只能确认文件已交给浏览器，不能据此宣称传输已完成。保存/复制时的 JSON 转换、画布布局等仍为同步计算，目前先绘制处理状态，尚未迁入 Worker。未对每个功能逐一连接真实 PLC 做压力测试，也不把增加 loading 称为消除了所有性能瓶颈。

本轮验证：Web 全套 66 个测试文件、308 项测试通过，类型检查通过；WPF Release 构建通过，0 警告/错误。包括并发请求状态、失败/取消清理、旧请求不覆盖新任务、100000 成员分页和实际删除索引等用例。之前依赖固定延时的取消用例已改为受控刷新阶段验证。

Docker 预览已更新至静态资源 `index-Cs6IcI8v.js`。隔离浏览器样例验证了点位请求等待提示、1200 点位填充成功后的恢复、503 失败后的恢复、设置读取的全局提示以及自定义 MID 新增入口隐藏；没有页面异常或写入请求。部署前后及浏览器验证后的工程 API 响应一致。截图和结果见 `artifacts/protocol-qa/loading-visual.json` 及 `loading-*-pending.png` 等文件。
