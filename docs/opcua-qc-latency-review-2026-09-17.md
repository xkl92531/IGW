# OPC UA / QC 读写延迟复查

检查日期：2026-09-17。代码基线：`fa0eef1`，包含工作区上一轮 QC 写入确认修复。

检查范围按用户澄清限定为仓库源码和当前工作区修复。本机安装程序尚未更新，不作为本报告的问题归因依据。离线复现项目通过 `ProjectReference` 编译仓库的 Core 和 OPC UA 驱动，不引用 `D:\Program Files\IGW` 中的已安装二进制。

结论：除了上一轮已修复的 QC 重复等待，本次确认了四个可导致额外延迟的运行机制，其中“持续读取超时被逐点重试放大”和“部分订阅拒绝引起整组重建”优先级最高。共享会话中这些操作会影响同一 PLC 上的其他工位。现场所述“读写都要几秒”与这些机制相符，但尚无现场请求轨迹，不能认定某一项就是唯一现场根因。

下文第 1–4 项记录修复前的调查证据。用户授权修复后，工作区已针对这四项实施修改；修复后的验证见文末。没有调整运行服务或向真实 PLC 发起读写，上一轮的前端修复仍保留。

## 已有订阅优化与 QC 修复覆盖了什么

调查时已逐项核对订阅优化提交 `48656c1`；调查基线 HEAD 的 Engine、SharedOpcUaDriverLease 和 OPC UA 驱动相对该提交没有后续差异。下表为修复前覆盖情况，不代表当前工作区仍有这些缺陷。

| 已有改动 | 覆盖场景 | 仍需区分的边界 |
| --- | --- | --- |
| MES 需求仍存在时，临时 QC 点延长保留 5–15 分钟 | 减少临时活动窗口到期导致的整组拆建 | 未处理服务器拒绝部分监控项造成的集合永久不相等 |
| 首帧等待 100–500ms | 给首次订阅通知机会，减少冗余补读 | 未限制后续补读内部的连续超时重试总量 |
| `BadRequestInterrupted` 改为 100ms 后快速重试 | 避免这类中断固定等待 5 秒 | 与持续超时和单点订阅拒绝不同 |
| 订阅失败清理 250ms、正常释放清理 500ms 取消预算 | 限制进入驱动清理后的服务调用等待 | 进入共享会话独占许可前的排队不包含在该预算内 |
| 当前工作区 QC 直接采用后台确认结果 | 取消后台已验证后再等最多 45 秒订阅值 | 后台验证自身的排队、批内重试仍然存在 |

因此，下面四个离线复现结论均基于包含上述改动的当前源码；没有把已解决的 QC 重复等待或临时活动窗口过期问题重复列为未解决问题。

## 1. P1：持续读超时会放大成大量逐点请求

位置：`src/IGW.Drivers.OpcUaClient/OpcUaClientDeviceDriver.cs:537`、`:560`、`:998`；`src/IGW.Core/SharedOpcUaDriverLease.cs:67`。

驱动把 `TimeoutException` / `BadRequestTimeout` 归为容量失败。批量读取超时后，按一半缩小批次；缩到一个点仍超时，只标记这个点失败，然后继续读取剩余每个点。当前逻辑没有该次逻辑读取的总耗时预算，也没有连续单点超时熔断。共享调度许可覆盖整个 `Driver.ReadAsync`，内部缩批和逐点重试不会让出许可。

离线直接调用生产 OPC UA `ReadCoreAsync`，保持连接状态为在线、每次服务读取注入超时：512 点产生 **521 次物理读取尝试**，请求大小从 `512 → 256 → … → 2 → 1`，之后逐点尝试，最终得到 512 个坏质量样本。

这是实际执行的次数，超时在复现中立即抛出。若每次恰好消耗默认 10 秒且会话始终被判定在线，理论累积为 5210 秒；这是条件推算，**不是现场实测**。连接断开、取消或部分请求恢复都会改变结果。

影响：一个坏批次长时间占据会话请求名额；两个名额均被慢读取占用时，优先写也只能等待，导致读、写一起慢。

修复方向：区分明确的服务器容量拒绝与超时；为单次逻辑读取增加总预算和连续超时阈值；缩批重试按协议批次释放调度权。保留真实错误质量和恢复能力，不把超时样本当作成功。

## 2. P1：一个订阅拒绝点会反复拆建整组正常订阅

位置：`src/IGW.Core/Engine.cs:1380`、`:1448`、`:1457`、`:1484`；`src/IGW.Drivers.OpcUaClient/OpcUaClientDeviceDriver.cs:416`。

候选集合包含所有需要订阅的点，但驱动返回的 `lease.TagIds` 只包含被服务器接受的点。下一次协调将“已接受集合”与“完整候选集合”比较，只要存在拒绝点就永远不相等，随后释放整个订阅并重新创建。需求稳定时，定期检查间隔为 2 秒；创建操作本身耗时较长或需求发生变化时，实际间隔会不同。

离线使用两个点、保持需求不变，只拒绝其中一个：推进模拟时钟 4.2 秒后，记录到 **创建 3 次、销毁 2 次**，包含正常点的订阅也被重建。这里使用模拟时钟，不是现场吞吐测量。

它与“订阅已接受，但首个数据样本为 Bad”的情况不同；现有首帧回退测试主要覆盖后者，不能发现本问题。

影响：正常点短暂停更、重复创建监控项、额外首值读取。共享会话的订阅释放需要独占许可，会扩大对其他逻辑设备读写的影响。

修复方向：分别保存本次请求集合、已接受集合和拒绝集合；需求没有变化时保留正常订阅，拒绝点独立退避/回退读取；允许后续恢复，避免永久忽略被拒绝点。

## 3. P1：写后回读丢失写优先级

位置：`src/IGW.Core/Engine.cs:2282`；`src/IGW.Core/SharedOpcUaDriverLease.cs:55`、`:58`；`src/IGW.Core/OpcUaConnectionPool.cs:124`。

共享会话只有 2 个并发名额。写协议调用使用优先队列，但随后的确认调用普通 `ReadAsync`，统一走非优先队列。写本身完成快，并不代表 QC 能快收到确认。

离线调用真实共享租约与调度器：先完成一次写入，安排两个在途读取和六个已排队后台读取，再安排写后回读。首次记录有 **6 个后台读取先下发**，本次重新编译核对时观察到 5 个。异步任务取得许可后，实际进入驱动的顺序存在并发差异；这个计数不是固定保证。源码和两次观察均表明，回读没有单独的优先级，会受既有普通读取排队影响。

若后台批次耗时较长，确认会等数轮读取；这项复现证明排队关系，没有测量现场网络耗时。写优先也不会抢占已经执行中的两个长读取。

修复方向：给写后回读传递显式操作类别/优先级，同时保留普通读取的公平性；限制长逻辑读取占用许可的时间。并发数应按 PLC 承受能力测量后调整。

## 4. P1：失败点拖延同批成功点和后续写入

位置：`src/IGW.Core/Engine.cs:2043`、`:2069`、`:2125`、`:2158`。

`WriteAndVerifyAsync` 允许初写加最多 10 次重写。已成功点虽然从重写集合移除，外层仍等整批结束后才完成每一个调用方的任务。同一逻辑设备的写泵也要等本批结束才处理后面的批次。

离线复现：Good 点与持续回读不匹配的 Mismatch 点同批。第二次写暂缓时，Good 的真实值已经发布到 DataHub，但它的写任务尚未完成；此时新排入的 Later 点也尚未下发。释放后，Good 写了 1 次、Mismatch 写了 **11 次**、Later 写了 1 次。

这解释“值已经变了，但操作迟迟不返回”。对 PLC 程序会立即复位的握手位，回读不匹配还可能触发重复写；是否存在这种现场逻辑，需要结合 PLC 程序和请求轨迹确认。

修复方向：每个点验证完成后立即完成其调用方；限制整批重试时间和连续占用写泵的时间，为其他点提供执行机会。握手/脉冲写要保留明确业务语义，不能直接将未验证结果当作成功。

## 5. P2：QC 超时不等于后台写已经结束

位置：`src/IGW.WebUi/src/utils/signalrTransport.ts:82`、`:88`、`:91`；`src/IGW.Northbound.RestApi/IgwRealtimeSignalR.cs:26`、`:49`；`src/IGW.Core/Engine.cs:386`。

浏览器 30 秒后通过 `Promise.race` 返回超时，但已发送的普通 SignalR invocation 会继续等待真正响应；服务器接收的是连接断开取消信号，没有每次请求的同等截止时间。设备队列取消逻辑仅在尚未开始下发时生效。

现有 `signalrTransport.spec.ts` 中“holds the lease for a sent invocation after its caller times out”测试实际验证了这一行为，本轮重新运行通过。

因此，超时后再次操作可能与原请求重叠；同一浏览器若积累多个长请求，还会占用每连接最多 8 个并行调用的容量。不能把“界面已报超时”解释成“PLC 肯定没收到”。

修复方向：增加请求标识和可查询的最终状态；对尚未下发请求提供截止时间；已经下发但结果未知时明确展示“结果未确认”，保持安全收尾，不自动重放。

## 6. P2：字符串写入每次都先读元数据

位置：`src/IGW.Drivers.OpcUaClient/OpcUaClientDeviceDriver.cs:667`、`:812`；`src/IGW.Drivers.OpcUaClient/OpcUaStringWriteFallback.cs:238`。

每次字符串写批次都会重新读取父节点 DataType 与结构体 DataTypeDefinition，读取 PLC 公布的字段容量；已有容量缓存也不能跳过该步骤。正常路径可能在实际 Write 之前增加两次网络往返，失败重试时还会重复。元数据接口慢会直接反映为写入慢。

这项是代码确认的额外路径，没有连接现场 PLC 测量。它影响 String/WString，不能用来解释截图里的 Boolean 点自身。

修复方向：按会话和数据类型版本缓存元数据，设置失效和失败退避机制；PLC 类型改变或长度拒绝时重新验证，保留防截断/越界的正确性约束。

## 7. 大数组需单独检查

位置：`src/IGW.Core/Engine.cs:2029`、`:2492`、`:2598`；`src/IGW.Drivers.OpcUaClient/OpcUaClientDeviceDriver.cs:549`。

调查基线中，数组写先于普通标量写被排空；数组切片写完成后，通过普通读取取回整个父数组再切片验证。读取请求没有 Value 的 `IndexRange`。因此，写单个数组元素也可能承担整数组传输和解码成本，多个数组操作会拖住后续标量写。本次已将数组验证接入优先入口，并将失败数组的重试改为每轮让出；完整父数组传输成本仍存在。

此项为静态路径确认，未做现场数组规模测试；截图中的普通 Boolean/Short/Float 点不能直接据此判定原因。

## 授权修复后的行为

本次验收重点是“失败点不额外拖住正常点”，同时保留真实 PLC 回读确认。

- **读取超时有界返回**：`TimeoutException`、`BadRequestTimeout` 和 `BadTimeout` 不再触发本轮二分加逐点重试。一次服务超时后保留已成功读取的前缀，未读取部分返回超时坏质量，下一轮采用较小窗口。明确的 `BadTooManyOperations` 等容量拒绝仍可拆批恢复。
- **部分订阅独立恢复**：完整请求集合与实际接受集合分开保存。需求未改变时保留已有正常订阅；拒绝点继续轮询，每 30 秒单独重试订阅。重试失败不清除正常订阅；全拒绝产生的空租约及时释放，实际需求改变或停机时释放所有租约。
- **写后回读优先、采集及时获得机会**：新增可选 `IWriteVerificationReader`，共享 OPC UA 租约通过优先队列执行验证。保留两个在途名额；普通读取有排队时，优先操作连续让行上限从 8 次改为 1 次，避免多工位持续写入和回读拖延采集。标量与数组验证均使用优先入口。
- **写入按点完成**：真实值和诊断先发布，已经完成验证的点立即返回，不等待同批失败点。未完成请求保留尝试次数、实际下发的规范化目标和原始代次，每轮后让出执行机会；正常点不会被再次重写。延后的读取分片出错不覆盖已经成功的结果，也不重复计为写失败。
- **数组失败让出**：每轮处理一个数组请求，再给标量机会；失败数组保存尚未匹配的切片，后续只重写这些元素。继续保留初写加最多十次重试、同数组新代次淘汰旧请求和下发后取消不得撤销 PLC 操作的语义。

物理边界：一个已经发出的 OPC UA 请求无法被后来的正常点抢占；整批服务超时不提供具体失败节点身份，因此无法保证同一物理请求中的健康点完全不等待。上述改动消除软件额外放大的等待，并保留后续恢复机会，不能替代现场网络、服务器和 PLC 响应时间测量。

### 后续读取与采集周期修复

用户补充“写入快、读取慢”后，新增门控测试复现了两个读取阻塞来源：并发驱动仍因写队列非空跳过扫描；采集循环的同步完成路径可能让独立写泵迟迟无法启动。现在分别调度采集与写入任务，并允许并发驱动在写队列有工作时继续采集。单通道驱动保持串行，不强行并发访问设备。

扫描与写入并行后，早于写后确认发出的读取可能更晚返回旧值。新增测试先让扫描取得旧值、再完成写后确认、最后释放旧扫描，修复前 DataHub 从 7 回退为 0。现在确认发布推进点位代次，且缓存发布与过期检查在短临界区内完成；旧扫描不能覆盖已确认值。锁不覆盖 PLC 网络调用。

QC 大快照分帧处理时，实时增量优先显示，并为快照保留推进预算；后续快照分片使用 store 的最新样本，避免显示值先更新再退回旧值。值和质量不变但样本时间更新时，刷新时间戳而不增加变化次数。

用户随后明确“失败值重写 10 次后仍失败就不再管”。据此撤销了前一轮新增的 MES 无限重试：普通周期 `Writeback` / `ResponseWriteback` 节点等待引擎给出最终结果，单次请求最多初写加十次重写；仍失败就保留失败记录并结束该项，不在 MES 层重新开启重试预算。当前流程所有节点结束后，从完成时刻起等待完整的 `CollectIntervalMs`，再进入下一轮。周期始终来自各任务配置，200ms 只是用户提供的现场示例，生产代码没有写死 200ms。下一周期是新的业务执行，不是上一请求的后台无限重放。

事件消费、协议指令/条码和旧式线性步骤保留各自原有恢复机制，不改变这些协议的重放约定。

### 多工位读取迟迟不发布的进一步检查

OPC UA 原先声明驱动自行拆批，导致采集计划把同一周期的全部点放入一个逻辑块。驱动内部按服务器窗口执行多次物理 Read，但只在全部完成后返回样本；第一批读到的值必须等最后一批，QC 和 MES 共同使用的 DataHub 因此一起延迟。

现在将 OPC UA 采集块按驱动物理窗口和字节上限拆开。每批完成立即发布、更新本批诊断并释放共享调度名额，后续慢批次不再扣住前批结果；驱动仍保留显式容量错误的内部缩批恢复。门控测试用 513 个点、512 点窗口，在第二次实际 Read 挂起时验证第一批已进入 DataHub 和 QC 式订阅消费者，覆盖全量与按需采集。修复前第一批在此时仍未发布。

“同一设备一个订阅”不等于“每个工位一个独立读线程”。原生通知按到达发布；同一 PLC 的读写请求仍共享两个在途名额，同一逻辑设备的回退扫描批次由采集循环推进。此轮消除了跨批统一发布和 8 次优先操作让行造成的软件等待，没有提高 PLC 会话并发上限，也没有证明现场所有 8 秒以上延迟均由这两处导致。
