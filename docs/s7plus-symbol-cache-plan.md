## 实施结果（2026-09-19）

第 1 节（1.1～1.6）已全部实施。

- Rust：`native/igw-s7plus/src/reader.rs` 负责符号缓存和单项隔离；ABI 升到 v2。
- .NET：`SiemensPlusNative`、`SiemensPlusTransport`、`SiemensSymbolicArrayCodec` 已同步修改。
- 测试：Rust 新增 9 个单元测试；.NET 新增和修改的传输层测试见 `SiemensPlusReadRecoveryTests`；后端全量 2009 项通过。

**PlcSim 回环实测**。方法：用 PlcSim 的 S7 Plus 模拟服务，直接调用原生 `read_batch`，每片 2048 项；耗时含模拟 PLC 本身。

| 规模 | 旧 DLL（ABI v1）稳态每轮 | 新 DLL（ABI v2）稳态每轮 | 连上后首轮（两者相同） |
|---|---|---|---|
| 10 万点 / 200 个 DB | 1.9～2.0 秒 | **0.14 秒** | 约 2.9 秒 |
| 35 万点 / 500 个 DB | 14.1～14.5 秒 | **0.53 秒** | 约 16 秒 |

**坏点隔离**：混入 1 个不存在的符号后：
- 旧 DLL：它所在的整片（数百到数千点）全部失败；
- 新 DLL：只有该点返回 `SymbolNotFound`，其余点全部正常。

**冷启动**：每次连上 PLC 后，首轮要把全部符号解析一遍，35 万点约 16 秒，与旧版每轮的耗时相当。如果现场认为这个时间太长，再按第 2 节“移植解析器”按 DB 批量解析来优化。

**构建说明**：本机 VS 2022 缺少 MSVC 的 C/C++ 头文件和 x64 库，而发行的 `igw_s7plus.dll` 一直是用 GNU（MinGW）工具链构建的，只依赖 Windows 系统库。现在的做法：
- `installer/build.bat` 在 MSVC 构建失败时，自动改用 `stable-x86_64-pc-windows-gnu`；
- GNU ld 不支持中文路径，所以先编到 `%LOCALAPPDATA%\igw-s7plus-target`，再拷回 `target\release`。

### 审阅后的补充（HSJM 会话审阅意见）

| 意见 | 处理 |
|---|---|
| Linux 仍是 ABI v1 的 `.so`，新托管代码严格要求 v2 会让 Plus 设备整体不可用 | 托管侧同时接受 v1 和 v2（`SiemensPlusNative.IsSupportedAbi`）。v1 结构体和函数签名不变，只是不会返回 `SymbolNotFound`：坏符号时仍整片失败，但只影响那一片，不再让整次读取失败。 |
| 断连/超时导致的解析失败不能当成“符号不存在”缓存 | 实现时已如此：`reader.rs` 的解析遇到 `is_connection_lost()` 或超时，整批上抛 `TransportFailure`/`Timeout`，不写缓存（有单元测试）；只有名字或成员查找失败才缓存 30 秒。 |
| 写入路径没用上缓存 | 写入改为走同一个解析缓存（`write_symbols`）。PLC 拒绝的项会作废其缓存地址。写入仍保持整批语义：任一符号找不到返回 `SymbolNotFound`，PLC 拒绝任一项返回 `ProtocolFailure`；**单项写入隔离本次不做**（见第 2 节）。 |
| 多项请求每一项都报错时，应按容量问题处理 | 同 crate `read_chunk_adaptive`：多项请求一个值都没回来时返回 `CapacityFailure`，由 .NET 缩窗重试，缩到单项后才按单项报告；避免把整批好点误判成坏点并隔离。 |
| 全部解析失败时不要发空请求 | 实现时已如此。 |
| 好坏点并存时，设备详情不要显示“符号不匹配” | 读取路径不再因单点或单片失败抛异常，设备详情显示“部分在线”并列出找不到的符号。 |
| 冷启动阈值写死 | 现场 34.5 万点连上后首轮超过 **60 秒**，就按第 2 节移植解析器（按 DB 批量解析）。模拟环境 35 万点为约 16 秒。 |

## 第二轮：性能与稳定性（原生 ABI v3）

与 HSJM 会话协同，把第 2 节里属于性能和稳定性的项做完。每项单独提交，测试全部通过。

| 项 | 做法 | 实测 |
|---|---|---|
| 写入单点隔离（38821a9） | 新导出 `igw_s7plus_write_items`，逐项返回结果：找不到的符号 `SymbolNotFound`、PLC 拒绝的项 `ItemRejected`（新结果码 35），其余项照常写入。多项报文被整体拒绝时，传输层对半拆分重写，直到隔离出被拒的那一点。托管侧对 ABI ≥ 3 的原生库用逐项写入，对 v1/v2 退回整批写入；数组写入只把失败的元素标为失败。 | PlcSim 回环：3 个好点加 1 个坏符号，一次写入，坏点返回 34，另外 3 点写入成功并回读一致。 |
| 程序下载后自愈（4c617a0） | 同一 DB（或区）在 60 秒内，对“之前解析成功过的地址”累计 3 次单项错误，原生层发出重建请求（`igw_s7plus_take_resync_request`）。传输层返回本轮已读到的值后断开会话；驱动下一轮重连并重新认证，符号缓存和 crate 的类型缓存随新会话重建。两次重建至少间隔 30 分钟；重建后触发它的符号仍出错，就视为真正的坏点，不再计数，由坏点隔离处理，避免反复重连。 | 单元测试覆盖阈值、窗口、限频和“重建后仍出错”的排除；驱动在传输层断开后重连会重新认证。 |
| P8 托管侧开销（a881131） | 先测再改：35 万点每轮的托管侧开销约 130～160 ms，其中一半是每片新分配约 1 MB 的输出缓冲。改为每个原生会话复用一块缓冲。也测过“点名 UTF-8 编码缓存到固定对象堆”，没有收益，没有保留。 | 每轮托管侧开销从 130～160 ms 降到 42～76 ms。 |
| M1 自有解析器（75a4d75） | 移植 crate 的解析逻辑（保留来源与许可说明）：DB 列表只取一次建哈希表，每个类型只取一次建“成员名 → 成员”表，取不到成员表的类型也记住。顺带修正 crate 的两处边界：数组下标越界一位不再被接受；M 区取不到类型时继续尝试 Q/I 区。 | PlcSim 回环，35 万点 / 500 个 DB（含结构体数组）：连上后首轮从 15.6 秒降到 **2.8 秒**，稳态约 0.5 秒不变；逐值校验与 crate 解析器完全一致。 |

仍未做：多维 BBOOL 数组元素编号的 crate 差异（只影响多维布尔数组，需要实机数据验证）、诊断统计接口、Linux `.so`（缺工具链）。

## 1. IGW 本次修改

### 1.1 单点失败隔离（P4 + P5，最高优先级）

**现状**：

- 包装层 `read_batch` 遇到空符号、非法 UTF-8，或者 crate `read_tags` 里任意一个符号解析失败，都会让整批返回错误。
- .NET 侧 `SiemensHybridDeviceDriver.ReadPlusAsync` 随后把本次调用的全部 Plus 点标为 `BadDeviceFailure`。
- 前面已经读成功的分片也一起丢掉。

后果：注册错一个符号，同一扫描周期组的全部点每个周期都是 Bad。另外，坏点自动隔离（`InvalidNodeReadPolicy`）只认 `0x8034xxxx`（BadNodeIdUnknown），而 Plus 路径从不产生这个码，所以隔离对 Plus 点从未生效。

**修改**：

| 层 | 改动 |
|---|---|
| Rust 包装层 | 新增结果码 `SymbolNotFound = 34`。<br>空符号、非法 UTF-8、解析失败都**按单项**返回 `SymbolNotFound`，只把解析成功的项发给 PLC。<br>PLC 对单项返回错误码时，也按单项返回。<br>只有连接断开类错误才整批上抛 `TransportFailure`。 |
| ABI | `abi_version()` 从 1 升到 **2**（结果码枚举新增值属于语义变更）。 |
| .NET `SiemensPlusNative` | 版本校验接受 v1 和 v2（v1 用于暂时只能构建旧版 `.so` 的 Linux）；`SiemensPlusResultCode` 同步新增 `SymbolNotFound`。 |
| .NET `SiemensPlusTransport` | `SymbolNotFound` 映射为 `BadNodeIdUnknown`（0x80340000），接入现有隔离策略（连续 3 次隔离、30 秒复探，策略本身不改）。<br>某一片失败时**保留已成功的样本**，只把失败片标 Bad；整体抛错只保留给会话级失败（断线、超时、认证、原生组件异常）。 |
| .NET `SiemensHybridDeviceDriver` | 不需要改：非会话级失败已经不再从传输层抛出，驱动也就不会再把本次调用的全部 Plus 点标为 `BadDeviceFailure`。 |
| 数组点 | 元素符号解析失败按元素标质量，不抛出整个 `ReadAsync`。 |

### 1.2 符号解析缓存（P1 + P2 + P3）

**现状**：

- crate 每个周期对每个符号都完整解析一遍。
- `datablock_list()` 命中缓存后仍然会复制整个 DB 列表，`type_info()` 每层都深复制一次。
- 34 万点 × 几百个 DB，每周期上亿次复制，CPU 高主要就是这个原因。
- 读回结果按项线性查找，单次调用复杂度 O(B²)。
- M/Q/I 区解析失败不缓存，每周期都会重新向 PLC 发 Explore 请求。

**修改**（都在 `native/igw-s7plus`，不 fork crate）：

- handle 上挂一个 `symbols: HashMap<String, CacheEntry>`：
  - 成功时缓存 `ItemAddress`；
  - 失败时缓存负结果，带 30 秒过期时间，期间不再解析、不再发 Explore。
- 读路径：逐个符号查缓存，未命中才调 `resolve_symbol`；只把成功项交给 `read_variables`；结果按 `item_no → 下标` 回填，复杂度 O(B)。
- 缓存失效：`connect` 或 `disconnect` 时清空，与 crate 自己的 `db_list`/`type_info_cache` 同寿命。
- 单项读回出错时，作废这个符号的缓存条目，下个周期重新解析一次。

### 1.3 真实容量错误（P6）

**现状**：Rust 侧从不返回 `CapacityFailure`（`lib.rs:181` 有注释说明），.NET 的缩窗路径是死代码，读窗口最大可以涨到 4096。如果 PLC 拒收大报文，这一组点会每个周期都失败，且不会自行恢复。

**修改**：PLC 拒绝整个请求（不是连接断开或超时），且请求不止一项时，包装层返回 `CapacityFailure`；单项请求被拒时，只把该项标为失败。.NET 现有的缩窗逻辑随之生效：对半缩小重试，缩到单项仍失败就只标该点，然后继续读后面的点。

没有在 Rust 里递归拆分：如果拒绝的原因其实不是容量，递归拆分会一次发出上千个请求；交给 .NET 缩窗，窗口在后续成功读取后还会逐步长回来。

### 1.4 输出缓冲重试（P7）

**现状**：输出缓冲不足（`BufferTooSmall`）时，.NET 会再调一次 FFI，等于把 PLC 再读一遍。

**修改**：记住上次实际需要的大小，下次直接按这个大小分配。

### 1.5 测试与验收

| 类别 | 内容 |
|---|---|
| Rust 单元测试 | 缓存命中/未命中；负结果过期；连接重建后清空；单项作废；乱序 `item_no` 回填；部分项出错；全部失败；拆半重试。 |
| .NET（现有 `ISiemensPlusNativeApi` Fake） | 1 个坏符号 + 999 个好符号 → 999 个 Good、1 个 `BadNodeIdUnknown`，第 3 周期起被隔离、30 秒后复探；<br>第 2 片失败时第 1 片的样本保留；<br>`CapacityFailure` 触发缩窗；<br>ABI 版本不匹配时报清晰错误。 |
| 基准 | 新增 S7 Plus 解析基准：10 万和 35 万符号时，冷启动（首轮解析）和稳态（缓存命中）的每周期 CPU。 |
| PlcSim 回环 | 1 万和 10 万点端到端吞吐。PlcSim 不返回单项错误、不拒收超大报文，这两条路径只能靠 Fake 覆盖。 |
| 实机（需现场配合） | 见 3.6。 |

### 1.6 构建与发行

- `installer/build.bat` 已包含 `cargo build --release`，Windows 的 `igw_s7plus.dll` 随安装包一起更新。
- Windows 安装包里的 DLL 与托管程序集同版本发行（ABI v2）。托管侧也接受 v1 的原生库（行为同旧版，没有单点隔离和解析缓存），其它版本号会被拒绝并给出明确提示。

## 3. HSJM 及其它接入方需要注意的点

### 3.1 注册契约不变

地址仍是符号字符串，设备名约定（S7 / S7Plus / GRAPH）不变，HSJM 的注册代码**无需修改**。

### 3.2 点位质量的含义有变化

| 情况 | 以前 | 以后 |
|---|---|---|
| 某个符号不存在或写错 | 同一扫描周期组的全部 Plus 点每个周期都是 `BadDeviceFailure` | **只有这个点**为 `BadNodeIdUnknown`（0x80340000），其余点正常 Good |
| 同一个坏点连续失败 3 次 | 一直参与读取 | 被隔离：不再发给 PLC，值保持 `BadNodeIdUnknown`，每 30 秒复探一次；复探成功或该点被重新注册后自动恢复 |
| PLC 拒收超大请求 | 整组持续失败 | 自动拆小请求，整组恢复正常 |

需要 HSJM 配合的地方：

- **按点判断质量，不要按组判断**。以前“一组全 Bad”可以当成设备故障；以后同一设备里 Good 和 Bad 会同时存在，诊断和判定逻辑都要逐点看质量。
- **`BadNodeIdUnknown` 表示注册的符号在 PLC 程序里找不到**，应提示“检查点名/PLC 程序”，不要当成通讯故障去重连或报警。
- 交接文档第 4 节提到的隐患④（“采集失败 ≠ 通过”）仍需 HSJM 单独处理：坏点现在只影响自己，但它的值依然是 Bad，不能被当成通过。

### 3.3 重连后的首轮读取会慢一些

- 解析缓存与连接同寿命。IGW 每次连上 PLC，首轮都要把全部符号解析一遍（冷启动）。第二轮改用自有解析器后，模拟环境下 35 万点首轮约 3 秒（原约 16 秒），之后每轮约 0.5 秒；现场数据以实机结果为准。
- 冷启动期间这台设备的值可能暂时还没更新。**连接刚建立时不要把“暂无新值”判为失败**，稳态以后每周期不再解析。

### 3.4 PLC 程序重新下载后

- 如果连接期间下载了修改 DB 结构（增删成员）的程序，缓存的地址会过期。**第二轮起 IGW 会自愈**：同一 DB 在 60 秒内有 3 次已解析地址被 PLC 拒绝时，自动断开并重建 S7 Plus 会话，重新解析全部符号。
- 重建期间点的质量按 `docs/dcs-read-quality.md` 的规则报告：设备断开时为 `CommFailure`，重连后首值未到时为 `WaitingForData`。重建后首轮会重新解析符号：模拟环境 35 万点约 3 秒。
- 自愈每 30 分钟最多一次；重建后仍然出错的点视为真正的坏点，走坏点隔离。
- 新增的成员不会触发自愈（旧程序里本来就没有），所以**给 DB 新增成员后注册的新点**如果一直是 `SymbolNotFound`，仍建议在 IGW 里对该设备断开再连接一次（禁用/启用设备）。

### 3.5 部署与版本

- 这次改动升级了原生组件 ABI（v1 → v2）。**只有用完整安装包升级才会生效**，不要只替换网关目录里的单个 DLL 或 .NET 程序集。
- 如果 HSJM 的 PlcSim 回环测试通过 `IGW_S7PLUS_DLL` 指向某个 `igw_s7plus.dll`，升级后要指向同版本的新 DLL，否则会因 ABI 版本不符被拒绝加载。
- Linux 部署：拿到构建工具链之前，Linux 版的 `.so` 仍是 ABI v1。新版网关同时接受 v1 和 v2，所以 Linux 上照常可用，但没有单点隔离（坏符号时整片失败）和解析缓存。

### 3.6 需要现场配合的实机验收

1. PLC1 全量约 34.5 万点注册后，Plus 设备连续运行 1 小时，记录：每周期 CPU、采集周期达成率，并确认没有整组 Bad。
2. 故意注册 1 个不存在的符号：只有这个点 Bad，第 3 周期起被隔离，其余点持续 Good。
3. 连接中重新下载 PLC 程序（改一个 DB 成员）：记录受影响点的表现。
