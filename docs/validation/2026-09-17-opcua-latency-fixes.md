# OPC UA 前三项卡顿修复与验证

对应 [2026-09-16 审查报告](2026-09-16-opcua-s7-latency-audit.md) 的 A、B、C。基于 1.6.59 源码修复；本次未修改 S7 驱动、配置格式和前端，尚未生成新版本安装包。

后续打包已完成：修复包含在 [1.6.60 安装包](../release-notes-1.6.60.md) 中，包信息及发布验证见发布说明。

## 修复行为

1. **部分订阅被拒绝不再反复重建整组**：保存完整的订阅请求点位及采样周期，与下一次需求比较；实际订阅集合仍只包含服务器接受的点。被拒绝点继续进入轮询，正常点继续接收通知。全部被拒绝也不会每两秒反复创建。实际需求或周期变化仍会重新协调订阅；被拒绝点不会单独周期性重建订阅，持续使用轮询，直到需求变化或重新建连。
2. **BadRequestInterrupted 优先重试**：收到第一次中断后，在当前调用内可取消地等待 100ms，再用同一会话尝试一次，期间不插入兜底轮询。第二次仍失败则恢复兜底读取，从失败完成时起退避 5 秒；需求刷新不再绕过该退避。这样不会无限优先重试而饿死采集。
3. **超时不再当成批量容量不足**：TimeoutException（含包装异常）、BadRequestTimeout、BadTimeout 都按当前批次失败处理，保留会话和批量窗口，交回调度器按周期重试。明确的 TooManyOperations 等容量拒绝仍支持缩批，保留已有正常点恢复逻辑。共享分类函数也不再让普通写超时进入容量缩批重发分支。

100ms 是首次中断后到下一次尝试的等待，不包含服务器处理、SDK 失败清理或成功后的首帧处理耗时，不代表任何情况下 100ms 内恢复全部数据。成功建立订阅后的大批首帧补读等其它审查项仍在后续范围内。

## 同一探针修复前后

|场景|修复前|修复后|
|---|---|---|
|一个点被拒绝、3 次需求检查|创建 3 次 / 释放 2 次|创建 1 次 / 释放 0 次|
|中断 + 注入 2500ms 兜底读取|约 2568ms 才重试，先读取一次|约 104ms 开始重试，之前读取 0 次|
|8 点持续请求超时|11 次物理请求，窗口降为 1|1 次物理请求，窗口仍为 8，返回 Block 级错误|

以上为本地可控故障注入，不是现场 PLC 性能测量。原始证据：[基线](driver-latency-audit/baseline-results.json)、[修复后](driver-latency-audit/opcua-fixed-results.json)。运行方式见原审查报告；探针仍会显示本轮未处理的 S7 问题。

## 回归证据

- 修改生产代码前，新用例及纠正后的超时分类用例出现 9 项预期失败：部分订阅重复建立、先执行慢补读、超时拆分/分类错误。
- 增加 12 个回归案例：部分/全部拒绝、拒绝点轮询、周期变化、重试顺序、连续中断不饿死轮询、取消、以失败完成时间退避且不可被需求刷新绕过，以及四种超时表现。现有一个“超时即容量不足”的测试预期同步纠正。
- 后端完整测试：**1617 通过，0 失败，0 跳过**。包含现有本机 OPC UA SDK 会话与读写验收；新增故障注入不访问现场 PLC。
- 完整测试结果：`artifacts/opcua-fixes-validation/opcua-fixes-full.trx`（本机构建产物，未纳入 Git）。
