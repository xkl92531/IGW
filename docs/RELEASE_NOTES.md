# IGW 发版说明

## 百万点 SSE 实时通道(sse-realtime-million-point)

- 单工程面向 100 万点：默认允许 100 个 SSE 实时客户端，每客户端精确订阅最多 10,000 点；低频配置与日志页面继续使用 HTTP，不挤占 PLC 采集和写入队列。
- Quick Client、设备状态和 MES 运行状态改为认证后的 POST SSE 推送，点值页面不再轮询 `/api/v1/values`；Quick Client 同时使用精确完整路径和虚拟表格。
- 初始及定时快照采用原子 `begin/chunk/complete` 协议，每 60 秒校准一次；增量按点合并，默认 1ms 批窗口，10 秒心跳。
- 有界队列、慢客户端隔离、丢弃计数、序号缺口和 `reset-required` 重同步共同保证背压不演变为无界内存增长。
- 工程点表变化会生成新版本，主动终止旧流、删除旧订阅并按新工程重建；断线期间保留最后值，20 秒无帧标记过期，恢复后自动重连和快照同步。
- `/api/v1/health` 增加实时流会话、队列、字节、重置及 P50/P95/P99 指标；新增可复跑的百万点、100 客户端、慢客户端、突发和工程热重载压力台架。
- 增量消息按 256 点/1 MiB 双边界拆包，慢网络写入有 10 秒上限；浏览器旧响应体在重连前强制释放，认证、配置、容量错误采用不同重试策略。
- MES/日志保存不再重启 PLC 和其他北向服务；实时拓扑版本只在点表、流策略或读取权限变化时提升。Quick Client 合并浏览器帧更新，MES 状态改为页面/任务精确订阅。
- 本机 30 分钟压力验证：100 万点、50 万活跃点、100 客户端、50,000 变化/秒稳态、200,000 突发、6 次热重载；总览 P50/P95/P99 为 5/20/20ms，所有层丢弃 0、最终值不一致 0、清理残留 0。详细证据和现场边界见 [验证记录](validation/2026-08-31-sse-realtime-validation.md)。

## MES 填入本组全部点修复

- 修复“填入本组全部点”点击后误切换为数据范围模式、映射编辑区消失的回归。
- 按钮现在只填充当前字段/结构映射，保持两套配置和当前模式；数组和索引子组继续自动压缩为逻辑结构，大映射仍按分页渲染。

## 自适应 PLC I/O 与故障隔离(adaptive-plc-io)

- OPC UA 在服务器未声明 `MaxNodesPerRead/Write` 时从保守窗口开始，遇到容量或请求超时自动减半并重编译扫描块；这是单次请求窗口，不限制工程总点数。
- OPC UA 活动 QC/监视点优先使用 Subscription；MES 和周期采集继续使用批量 Read，订阅建立失败会自动回退读取而不会让设备离线。服务器能力按端点和服务器身份持久化，重启后不再从头试探。
- OPC UA 客户端默认采用首次信任并固定证书指纹（TOFU）；证书意外变更不会被静默接受，同时仍保留严格校验和显式全接受兼容模式。
- PLC 点位、地址、权限、类型、块容量和单次超时不再导致整台设备/整条通道断开；只有协议明确返回会话关闭或传输探测失败才重建连接。
- 写入优先于剩余读取块执行；所有已接受的可读写点均回读验证，不一致点最多选择性重写 10 次。只读、不可写和类型拒绝立即隔离，不重复冲击 PLC。
- 同一数组的新写入会以代次替代旧写入；旧代次在排队、回读或重试阶段都会停止，避免高速业务把过期值再次写回 PLC。
- Modbus TCP 连续寄存器/线圈和 Mitsubishi MC 连续地址启用协议原生批量读写；写失败按点或块返回，不再把单点错误升级成连接断开。
- 自动调度优先级固定为 PLC 写入/回读验证、MES 流程读取、QC 交互读取、后台普通采集，用户无需配置“快速通道”。
- EtherNet/IP 整批 Bad 会先独立确认 TCP 传输状态，避免一个错误标记让健康会话被误判离线。
- REST 写失败响应增加精确 `quality`、`statusCode` 和 `statusHex`，设备统计增加写队列、协议响应、回读验证 P95、同会话重试及批量降级计数。
- Web 工程页、监控页、日志页和 IGW 设置改为按路由加载，Element Plus 不再全量注册图标；大型工程的参数/数组范围沿用分页与虚拟列表，避免一次渲染上万编辑器。
- 合成压力回归覆盖 100 万元素、50 台设备、1,000 次写入回读验证、部分坏元素隔离和零异常断线；本机 Modbus TCP REST 读写闭环通过。现场 PLC 验证边界见验证记录。

## MES 流程模板(mes-flow-template)

**新增能力**:画布上配好的采集任务可一键「存为流程模板」,套用到任意主标记组一键生成任务(点引用自动按 源组→目标组 前缀深度重写);支持批量套用(勾多个组/按设备模板实例圈选,原子提交)、套用报告(目标组缺点 missing/组外引用 external,不静默)、模板导出导入 JSON。入口:画布工具栏「模板 ▾」。

- **印章语义(与设备模板不同,务必周知)**:流程模板套用即拷贝、**与模板断开关联**——之后改模板不影响已生成的任务,删模板任务也不受影响。设备模板是"活关联"(改模板全场跟进),两者刻意不同:任务天生要被个性化(触发条件/工位号/报文),活关联的合并语义过重。
- 套用产物默认**停用**,review 触发条件后手动启用(与画布自动建任务惯例一致)。
- 兼容:旧工程零改动;用了流程模板的工程在旧版本打开会丢模板库字段(单向门,与设备模板同性质;已生成的任务不受影响)。

## 数据面单机 100 万点(dataplane-1m)

**能力升级**:变化总线分片 + 订阅倒转 + 整型句柄/变体值贯穿 + 背压可观测 + 1M 基准台架。单机 100 万点、10 万变化/秒稳态,数据面不再是规模墙。

### 基准数据(参考机:i7-10750H 6C12T / 32GB / Win10,`tools/DataplaneBench`)

| 档位 | 指标 | 实测 |
|---|---|---|
| **1M 全量**(2000 设备 × 500 点,10% 活动点,8 分片,30s) | 稳态吞吐 | **99,878 条/秒**(目标 100k 的 100%)|
| | 发布→消费延迟(稳态) | p50 = 6.4ms,p99 = 80.6ms |
| | 稳态丢弃 | **总线 0,全量订阅 0** |
| | GC(20s 稳态窗) | gen0 = 6,gen1 = 2,gen2 = 1;分配 ~71 MB/s(驱动侧短命箱,按设计保留)|
| | 内存 | 工作集峰值 ~1.0 GB(含 2000 条设备循环)|
| | 启动 | 1M 点绑定+注册 数秒级;启动突发(全点 坏→好 一次性 ~1M 条)按设计有界丢弃并**计数可见**(全量订阅丢 ~35 万,总线视时序 0~4 万)|
| **冒烟**(20 设备 × 500 点,8s) | | 吞吐 1,000/s(100%),稳态 gen0 = 0(热路径零装箱实证),零丢弃 |

复跑:`dotnet run -c Release --project tools/DataplaneBench`(1M 档)/ `-- --smoke`(万点冒烟);通过判定 = 稳态窗零丢弃 + 吞吐 ≥ 目标 90%。

### 行为与兼容

- **对外零变化**:REST/OPC UA/MQTT/历史 输出的值类型与语义逐位不变(变体按原始 CLR 宽度还原);`.igwproj` 格式不变;**无单向门,可直接回退**。
- **仓库内部 API 变更**:`IDataHub.Subscribe` → `SubscribeAll` / `SubscribePoints`(点注册,计数化 Add/Remove);`TagChange` 增 `Handle`;`DataValue` 变体化(`Value` 属性兼容)。五个内部消费方已随改:Alarms/Computed/OPC UA 推送改点注册(成本 ∝ 关心点数),DataLogger/MQTT 全量。
- **丢弃不再静默**:每分片/每订阅的 深度/丢弃 计数经 `/health.dataplane` 暴露,监控中心常驻展示(丢弃标红,不弹告警)。DropOldest 有界策略保留——内存有界是底线,丢弃必须可见。

### 墙③(OPC UA 1M 节点)立项输入

本次订阅倒转后,UA 推送的"进入成本"已降为 ∝ 被钉点数(原来每条变化都过一次 IsPinned 字典查找)。剩余瓶颈(实测范围外,留给墙③ change):
1. `CreateAddressSpace` 一次性构建 1M `BaseDataVariableState` 的内存/耗时;
2. `PushValue` 持 NodeManager 全局锁逐点推送 —— 大量监控项 + 高变化率下锁竞争,需要批量推送/分区锁;
3. 单会话大订阅的 Publish 队列(`MaxNotificationsPerPublish`)吞吐。

## 设备模板化配置(device-template-config)

**新增能力**:设备模板与批量实例化 —— 提取模板、套用建设备、套用后自动验证(可浏览驱动匹配 / 不可浏览驱动试读)、实例差异(覆盖/追加/屏蔽)、改模板全场跟进、CSV 批量导入、运行时点位展开(工程文件体积与设备数解耦)。用法见 [设备模板.md](设备模板.md)。

### ⚠ 兼容性:单向门(务必周知现场)

- **旧工程零改动可加载**:从不使用模板的既有 `.igwproj` 照旧运行,校验不产生模板相关告警 —— 升级本版**安全**。
- **用了模板的工程不可用旧版本 IGW 打开(单向门)**:一旦工程里创建了模板并用「套用/批量导入」建了实例,该 `.igwproj` **只能用本版本或更新版本**打开。旧版本不认识 `templates` 与设备的 `templateRef`/`delta` 字段,加载后模板实例会变成**没有点位的空设备**(静默丢点),不是显式报错。
- **建议**:回退旧版本前,先确认工程未使用模板;或保留升级前的工程文件备份。数据目录(`ProgramData\IGW` / `/var/lib/igw`)在升级/重装时不动,工程文件不会被安装程序覆盖。

### 实现要点(供维护者)

- 模型:`IgwProject.Templates`、`DeviceTemplate`、`DeviceDef.TemplateRef` + `DeviceDelta{Overrides/Adds/Masks}`(均为可选字段,`WhenWritingNull` 序列化 → 旧工程缺省)。
- 运行时:`TemplateExpander` 在设备绑定前把「模板 + 差异」展开为有效点集(覆盖→屏蔽→追加),下游(DataHub 注册、扫描分组、北向、MES 组引用)对模板无感。未改点引用共享模板对象(零拷贝),面向规模。
- 热重载:`RuntimeEngine.DeviceSig` 纳入所引用模板的内容哈希 —— 改模板则全体引用实例签名变、`ApplyAsync` 只重启这些设备且差异保留;改单实例差异只重启该实例。改模板会触发批量重启,`ApplyAsync` 分批启动(每批 100 台)防重连风暴。
- 校验:`ProjectStore.Check` 返回 `ValidationReport{Errors,Warnings}` —— 模板名唯一/引用存在/驱动一致/追加重名为**错误**(阻断保存),悬空覆盖/屏蔽为**警告**(放行,展开时忽略);`Validate` 有错抛。
- 规模:20 模板 × 2000 实例(展开约 10 万点)工程文件为百 KB 级(逐点物化会是数十 MB);已有单测基准 `TemplateScaleTests`。
